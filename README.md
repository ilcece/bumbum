# BUMBUM NFC 数字项目

为服装、饰品等实体物品嵌入 NFC 芯片，提供物品信息、防伪验证、所有权绑定与数字互动体验。

维护人 cece 是产品经理，没有编程基础，但能理解逻辑、操作命令行，并照步骤完成构建和验证。项目文件以 cece 能读懂为标准：先用大白话讲目的、流程和结果，必要术语配中文解释，复杂参数放到有链接的技术附录。详细要求见 [AGENTS.md 的可读性原则](AGENTS.md#7-文件可读性以-cece-能理解为标准)。

## 当前实际状态

- 当前规划：Phase 1，管理员基础闭环；阶段范围与验收以 [PRD.md](PRD.md) 为准。
- 仓库目前只有需求、技术设计、接口契约和目标 DDL，没有后端、前端、依赖清单、迁移或测试代码。
- 文档和 DDL 的存在不表示应用已经实现、数据库已经部署，或真实芯片已验证。
- 已确认：全局 K1 先解开链接中的芯片编号，每枚芯片自己的 K2 再核对防伪码；其他密钥按项目、芯片编号和用途分别计算。初期只用 K1 的 v1，先解出编号再查所属项目，见 [密钥说明和流程图](TECH_SPEC.md#31-各把钥匙负责什么)。
- 全局 K1 泄露会影响该版本全部芯片的 UID/计数器隐私。具体访问权限、派生算法和写卡参数仍需核验及真实单卡测试；养成权限与用户身份方案仍待确认。当前不生成生产密钥或批量写卡。
- NFC.cool 能力、Webhook 负载及库兼容性缺少可复查的版本和测试记录，验证要求见 [尚未完成的检查](TECH_SPEC.md#9-还有什么没验证)。

## 技术栈与业务边界

- Python 3 + Flask；MySQL 8.0；React + Vite + TypeScript。
- Gunicorn + Nginx，目标部署在阿里云 ECS；数据库使用阿里云 RDS。
- 一个仓库、一个 Flask 应用、一个数据库；共享逻辑放在未来的 `core/`，业务按 `fashion` / `jewelry` 隔离。
- 两个前端 SPA：`nfc.bumbum.cc` 用户侧，`admin.bumbum.cc` 管理端。`bumbum.cc` 品牌页可选。
- 芯片目标为 NXP NTAG424 DNA；真实写卡工具与能力需要按版本核验。
- 已提供的资源记录：阿里云 ECS（用户记录 Ubuntu 26.04，部署前核验实际版本）、RDS、备案中的 bumbum.cc、iPhone（iOS 14）、Windows 11 和 MacBook Air 2024。
- 不引入微服务、Redis、消息队列等额外基础设施；变更技术栈须先提出理由并获 cece 确认。

## 开始工作

1. 阅读 `AGENTS.md`，确认本次目标和当前阶段；其他工具可粘贴 `.ai/SESSION_START.md`。
2. 按任务读取 PRD、技术规格、对应 API 和相关表结构。
3. 当前没有可执行的安装、启动或测试命令，不要假定 `app.py`、`requirements.txt` 或 `frontend/` 已存在。
4. 后续代码加入时，补充实际验证过的版本、安装命令和运行检查，再更新本节。具体安全和部署实现还须读取技术附录。

## 配置与数据库

- 配置项以 `.env.example` 为清单。需要本地运行时可复制为 `.env`，仅在本机安全填写；本轮未创建真实 `.env`。
- MySQL 最低要求为 8.0.16，以保证 DDL 中的 CHECK 约束实际生效。执行前确认目标是空库且连接正确；不要在已有 RDS 上直接重跑 `db/schema.sql`。
- 后续已有数据库变更需要独立迁移、备份和验证，不能通过修改目标 schema 冒充完成升级。
- 云开发环境与生产 ECS/RDS 是不同环境。当前不需要生产密码，也未验证生产连接。
- 前端只能使用公开的 `VITE_` 配置。API 地址拼接的唯一规则见 `API_CONTRACT.md` 第 0 节。

## 当前开发顺序

先落实 Phase 1 的认证、入库、物品和绑定管理；全局 K1 密钥架构已经确认，密钥生成与真实写卡须完成具体权限、算法、参数核验及单卡测试。Phase 2 再实现用户侧在线验证和短信绑定，Phase 3 再实现业务运营和养成。文档修订与业务代码生成是独立任务。
