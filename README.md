# BUMBUM NFC 数字项目

为服装、饰品等实体物品嵌入 NFC 芯片，让用户用手机碰一下，就能查看资料、验证真伪、绑定所有权，并在后续体验数字互动。

维护人 cece 是产品经理，没有编程基础，但能理解逻辑、操作命令行，并照步骤完成构建和验证。**项目文件以 cece 能读懂、判断、操作为标准：先讲目的、步骤和结果；必要术语用大白话解释。**具体要求见 [文件可读性原则](AGENTS.md#7-文件可读性以-cece-能理解为标准)。

## cece 怎么读这些文件

1. 判断“要做什么、怎样才算做完”：读 [产品需求](PRD.md)。
2. 理解“碰一下后发生什么、怎样防伪和登录”：读 [运行说明](TECH_SPEC.md)。
3. 核对“页面要提交什么、会收到什么”：读 [接口说明](API_CONTRACT.md)。
4. 让 AI 开始工作：使用 [会话模板](.ai/SESSION_START.md)，写清任务和可检查的结果。AI 再按任务查技术附录、数据库和配置文件。

cece 可以先读正文判断流程，按需查技术附录；AI 写代码时必须读对应的精确规则。需要执行命令时，说明必须包含执行位置、预期结果和失败后的处理方法。

## 选用的工具和业务分工

| 部分 | 使用什么 | 负责什么 |
|---|---|---|
| 用户页、管理页 | React + Vite + TypeScript | 浏览器中看到和操作的页面 |
| 后端 | Python 3 + Flask | 接收页面请求，检查身份，处理业务 |
| 数据库 | MySQL 8.0 | 保存芯片、物品、用户和操作记录 |
| 正式运行 | Gunicorn + Nginx | 分别运行后端、接收网站访问并转交请求 |
| 云服务 | 阿里云 ECS、RDS | 分别提供运行程序的服务器、托管数据库 |

一个仓库、一个后端、一个数据库。共同功能放在 `core/`；服装 `fashion` 和饰品 `jewelry` 的业务分开组织，避免同一功能写两遍。

计划两个网页应用（SPA，主要由浏览器切换页面），当前已建立管理端检查、登录与芯片登记页：`nfc.bumbum.cc` 给用户，`admin.bumbum.cc` 给管理员。`bumbum.cc` 品牌页可选。芯片目标为 NXP NTAG424 DNA；真实写卡工具仍需按版本核验。

已有资源记录：阿里云内地ECS（系统待核验）及香港ECS（cece确认Ubuntu 22.04、2核4GiB）、RDS、备案中的 bumbum.cc、iPhone（原记录iOS 14，实测时核对当前版本）、Windows 11 和 MacBook Air 2024。扫描测试建议使用香港ECS和test.bumbum.cc，域名及HTTPS入口已由cece配置，手机扫描尚待验收；细节见技术说明第2.5节。当前不增加微服务、Redis、消息队列等额外运行服务，避免维护负担。改变所用工具和部署方式前，须说明理由并获 cece 确认。

## 代码和配置在哪里

后端入口是 `app.py`，手机扫描在 `core/scan_webhook.py`，共用登记规则在 `core/chip_registry.py`，数据库连接在 `core/db.py`，认证与账号命令在 `core/admin_auth.py`、`core/admin_cli.py`，芯片登记查询在 `core/admin_chips.py`，当前前端在 `frontend/admin/`。`compose.yaml` 只启动独立测试数据库；首次给空库建表使用 `db/schema.sql`，已有库升级仍需另写迁移。

云测试部署依赖在requirements-deploy.in/txt，通过容器固定版本，不替换Ubuntu系统Python。Python 的本机直接依赖在 `requirements.in`，完整固定版本在 `requirements.txt`；开发检查对应 `requirements-dev.in` 和 `requirements-dev.txt`。前端依赖与固定版本在 `package.json`、`package-lock.json`。更新依赖时同步对应清单，不手工改锁文件凑版本。

`.env.example` 是配置模板，准备脚本生成本机 `.env` 并保留已有文件。`VITE_` 配置会进入网页，只能放公开信息；接口地址拼接规则见 [接口说明](API_CONTRACT.md#01-地址和字段)。云开发环境与生产 ECS/RDS 分开，本轮没有连接生产数据库。
