## 2. 当前随机密钥与主密钥派生的区别

现有规则：每标签独立生成5个16字节随机数，格式为32个十六进制字符。没有主密钥、没有由UID计算的规则，不能凭UID恢复；数据库指纹也不可逆。

派生方案使用高熵主密钥和标准KDF，根据稳定元数据确定性生成每枚、每槽、每代的AES钥。算法可以公开，安全性依赖主密钥保密，不依赖隐藏规则。

建议主密钥32随机字节（64个十六进制字符），与每把芯片AES128密钥16字节（32字符）区分。不要复用SESSION_SECRET、管理员密码或人类口令，不把UID单独哈希当密钥。

### 待评审的精确HKDF提案

```text
算法：HKDF-SHA256
IKM：32字节随机主密钥 M
salt：UTF-8("bumbum/nfc/kdf/v1")
info：UTF-8("bumbum/ntag424dna/key/v1\0")
      || UID的7个原始字节
      || KeyNo的1字节整数（0–4）
      || generation的4字节无符号大端整数
输出长度：16字节
```

上式的`\0`拟表示单个NUL字节，不是反斜杠加数字0。正式实现必须锁定编码、顺序、长度、代次起点、边界和测试向量；此处只是提案，不能当成已交付工具的现行规则。

- 不同UID、不同槽位、不同generation生成不同钥。
- masterKeyId只定位所用主密钥，实际元数据必须持久保存，不能猜当前版本。
- 项目/生产与测试根密钥分开；不绑定服装名称、手机号、可变域名或随机入口码，避免业务编辑触发换钥。
- Key Version芯片字节范围有限，不作为完整代次历史的唯一记录。
- 若供应链要求NXP AN10922/AES-CMAC分散或SAM兼容，应在实施前另选并验证标准；不能声称HKDF与第三方App的master-key/口令派生相同。

### 推荐信任边界

```text
离线/受保护主密钥 → 初始化工具派生每枚Key0–4
                        ├─ 现场用十六进制写入芯片
                        └─ 只将每枚Key1/2交给当前Web运行文件
```

主密钥不放Git、不打入镜像、不注入长期运行Web，也不直接填入nfc.cool口令框。主密钥至少两份受控加密离线备份，恢复须演练。单枚钥泄漏不应揭示其他标签；根钥泄漏则影响其下所有派生钥，因此根钥需更严格保护。

未来可使用KMS/HSM，但必须核实服务是否支持所需派生/解密能力和可用性；当前没有集成这些服务。

### 元数据与迁移要求

每枚/每槽至少记录：UID、key_source(random/derived)、算法版本、masterKeyId、generation、密钥版本、目标指纹、写入/验证状态、操作人和时间。目标值与实际值分开，保留必要旧钥恢复条件但不能公开。

1. 现有随机标签继续使用原文件，不通过“指定新主密钥”反向变成派生标签。
2. 新标签先使用派生；后端同时兼容两类来源。
3. 老标签迁移时需现场认证旧钥，实际写入新钥，再配套更新运行文件/数据库指纹和状态；不能仅替换文件。
4. Key1/2会影响实时验真，须安排维护和失败恢复；不能清零读取计数掩盖迁移。
5. Key0单独换代不要求改变Key1/2，避免所有槽位一起无谓轮换。
6. 失去当前旧Key0/认证条件，不能靠新主密钥恢复芯片控制权。

## 3. 管理后台与用户域名隔离

当前同域名运行合法且已做认证；“后台网址可见”不等于未授权可访问，但独立域名便于隔离策略。

建议用户入口继续`nfc.bumbum.cc`，后台改为`admin.bumbum.cc`，同ECS/应用/数据库可继续使用。**保持用户域名和/v路径不变，可以避免重新写卡。**

需要协同实现：

- 新增后台origin配置与管理API来源校验，用户PUBLIC_BASE_URL仍用于生成NFC入口。
- Caddy在用户域名拒绝/admin和/api/admin；后台域名按需求只暴露管理页面/API/必要静态资源。
- 应用同时进行主机/来源与权限控制，不只依赖一条DNS解析；不让其他Host绕过。
- Cookie仅后台主机、Secure/HttpOnly/SameSite；当前已无Domain，但当前同域名，尚未实现此分流。
- 可选VPN/IP策略或额外身份认证；不要把IP限制误用于消费者入口。
- 正确DNS/两站证书、退出/会话迁移、CSRF、跨域静态资源、默认Host与路径编码绕过测试。

只改DNS/Caddy而不改应用origin会破坏登录写请求。示意配置名ADMIN_BASE_URL当前没有实现，不能直接添加期待生效。

## 4. Excel / CSV批量导入

建议第一期只做新增服装、登记真实UID、按服装实例编号绑定。导入不是实体写卡。

| 模板 | 建议字段 |
|---|---|
| 服装 | item_code、name、brand、style_code、color、size、material、description、care_instructions、image_url、status |
| 标签 | uid、garment_item_code、notes |

流程：下载模板→上传→预览/校验→确认→导入结果及失败明细。

需先确定：整批失败还是逐行/分批事务；新增与更新模式；字段留空含义；重复UID/编号/已绑定服装的处理；幂等批次和审计；大文件限制与编码；错误行可重试；Excel公式/CSV导出注入；失败文件不泄露秘密。

默认不覆盖已有资料，已有记录更新需显式选择、版本控制和变更预览。复用现有唯一/绑定/审计规则，不能通过批量接口绕过。

批量生成入口/密钥是后续独立功能，需要权限、受保护交付和完整写入台账。每枚芯片仍需近场初始化及回读，上传Excel不能远程替3枚标签写钥。

## 6. 数据库和基础设施后续

SQLite用于当前单机验证，后续迁移托管MySQL应基于写并发、数据量、备份恢复与高可用要求。迁移要保留UID、entry_code、绑定、审计和最大计数，否则可能导致已写卡失效或重放保护倒退。

选择普通事务型MySQL/InnoDB，不能仅因产品显示MySQL协议/版本号就选分析型DuckDB实例。MySQL模式继续遵守运行与迁移账号分离、最小权限、真实TLS和内网连接。

OSS适合图片和受保护备份，不替代关系数据库，也不承载活动SQLite文件。大陆ECS/ICP是讨论过的方案，当前仍香港；实际购买和备案政策需当时核对，不把历史截图价格/试用额度作为采购承诺。
