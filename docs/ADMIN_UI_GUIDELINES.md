# 管理后台设计与交互规范

本规范用于管理后台后续页面及原型调整。cece已同意以其2026-11-04上传的最新版《设计项目管理后台.zip》**原始文件**为展示基准，以Ant Design 6提供控件、状态和通用交互。此前AI修改稿不作为基准。本规范的批准不代表现有界面已符合规范，也不代表新业务已经实现。

业务定义见[产品入口](../PRD.md)，新增业务见[后台重构提案](proposals/admin-make-rebuild.md)及[D接续提案](proposals/replacement-resale.md)；这里不另定业务权限、额度或状态机。接入方式见[前端协作](FRONTEND_COLLABORATION.md)。

## 1. 原始 Make 提取的视觉与框架基线

来源为原包的`src/index.css`、`src/App.tsx`及`src/components`内页面。下面尺寸是该原稿的参考基线，不能归称为Ant Design对所有后台的强制尺寸。修改基线或主要容器前先说明原因并对齐。

| 部位 | 原稿基线及使用方式 |
|---|---|
| 主题 | 浅色；主色`#1677ff`，圆角8px；背景`#f5f7fa`，正文`#0f172a`；侧栏、顶栏、卡片白底，辅助文字和边框用灰色层级 |
| 字体 | Inter、系统西文字体、PingFang SC、Microsoft YaHei、sans-serif；编号、时间与正文统一字体，数字使用tabular-nums，不另强制等宽字体 |
| 应用框架 | Ant Design Layout/Menu；左侧栏248px，顶栏58px、左右内边距24px；顶栏右侧聚合管理员身份、会话状态和退出登录，使用真实会话 |
| 内容区 | 内边距20px，居中最大宽1440px；桌面最小宽1024px、最小高640px；应用壳高100dvh |
| 滚动 | 保持顶栏/侧栏位置，主内容区独立滚动；侧栏菜单可独立滚动；Modal/Drawer在自身容器内滚动。矮窗口仍能到达操作栏，避免多层不必要滚动 |
| 间距 | 常用区块间距16/20px；细节沿用4/6/8/10/12/24px层级，不为每页另建一套尺寸 |
| 查询区 | 小型Card，内容内边距16px 20px，表单列间距12px；常用条件先展示，高级条件展开；常规单行控件高32px |
| 列表 | 当前重构目标的可分页数据表每页最多10条，不提供超过10条的选项；候选选择表可保留5条。Table使用middle密度，操作按钮small；身份链接突出，名称、状态及日期保持主次；必要时表格内部横向滚动，操作列固定右侧，原物品表参考宽1020px |
| 详情与新建 | 原稿物品详情Drawer宽680px；本次cece要求物品/芯片详情统一试用800px，新建物品Modal仍宽520px；内容按分组排列，不把低频高影响流程堆在详情顶部 |
| 资料编辑 | 原服装资料Modal宽1040px；本次共用资料编辑及多步办理使用1120px居中Modal，左表单、右用户视角预览；宽窗口列比例14:10、间距24px，字段列间距12px；空间不足时合理收拢，不能截断操作 |
| 登录 | 延续原稿的身份验证层次和清晰反馈；验证码格参考42×42px。保留真实密码/TOTP、会话恢复和退出，不移植假登录 |

## 2. 页面组织与操作位置

默认路径：列表定位 → 详情核对身份和当前事实 → 在相关分区发起操作 → 专注完成修改或处理 → 保存/确认 → 返回原上下文。

- 重构业务文案统一称“物品类别”：只在款式资料维护，发行/物品/实体/芯片按关联取得；展示和筛选不增加独立录入入口。未关联时不猜测类别。具体来源与现有project兼容边界见[重构提案第2.4节](proposals/admin-make-rebuild.md#24-已同意的三层信息与字段展示)；隔离原型已按此改名并调整引用，正式页面/接口仍待整合。
- 列表标题、统计摘要、查询、结果和批量/行操作各有位置。主要动作突出，危险动作有明确文字和影响确认，不能只依赖红色或图标。
- 物品详情保留原稿的分组阅读方式，按已同意的字段细化为“基本信息 → 日常维护 → 商品资料 → 当前实体与历史实体 → 数字权益与办理记录 → 所有权流转记录”。顶部先展示稳定身份、限定编号、当前归属及状态摘要。
- 芯片动作放在“状态与芯片管理”；物品关联动作放在“当前实体与历史实体”；数字权益和履约操作靠近相应权益/服务信息。芯片页可携带上下文进入同一业务流程，不维护第二套接续逻辑。
- 界面使用“实体”“当前实体”“历史实体”“第几次交付”等直观名称，避免“载体”“载体代次”；不改变旧记录的业务含义。按共用款式/发行资料、每件数字物品身份、每次交付的实体信息分层，详细字段落位见[重构提案第2.4节](proposals/admin-make-rebuild.md#24-已同意的三层信息与字段展示)。日常维护只放操作，不重复一套录入表单；目标按共用款式统一维护并同步引用，实体交付记录独立；正式应用尚待迁移。
- 不在物品详情抽屉最上方增加挂失/换新/转售大面板。原稿的换芯片按钮也不能直接等同于已批准的完整换新/转售流程。
- 简单确认可用Modal；资料编辑用适合表单宽度的Modal/页面；已对齐的换新/转售使用1120px居中大弹窗，承载申请、准备、履约、正式接续和历史，内部滚动且底部按钮可达。不在窄抽屉叠加完整多步业务。
- 尺码只在款式尺码资料、实体交付及换新目标等相关位置出现；挂失摘要不突出，转售申请不要求尺码，转售准备阶段记录本次交付尺码。共用资料保存展示受影响的引用物品数量，多件受影响时确认后保存。
- 未交付的所有权、清理、日志等功能不因原稿存在菜单就变成正式入口；本轮信息架构已通过：5个一级入口，物品管理内用4个二级工作区；实体/持有人/年度权益/流转通过详情关联，具体职责见[重构提案第2.1节](proposals/admin-make-rebuild.md#21-信息架构与功能职责)。后续是否新增一级菜单仍由实际需要对齐。

## 3. 查询、详情、编辑和上传

| 场景 | 交互要求与官方组件复用 |
|---|---|
| 查询 | Form/Input/Select/DatePicker及查询/重置按钮；区分输入中与已生效条件，查询后分页回到适当位置；收起高级条件不清空条件，重置含义明确；优先复用官方组合及现有查询适配 |
| 芯片默认排序与新增定位 | 登记时间倒序，同一时间按内部编号倒序保证稳定；维护时间变化不视为新登记。手工/Webhook新增成功后回第一页，保留当前筛选；若新记录不匹配筛选，成功提示提供确切记录入口，不伪造结果。重复回调不改登记时间或强制跳页 |
| 列表返回 | 从结果打开详情或关联物品后返回，保留已生效条件、分页及必要定位；明确URL、刷新和直接访问的行为，不能把原稿display保活当完整方案 |
| 关联引用 | 芯片关联物品显示可识别的身份/名称链接，点击查看物品详情并可回到来源；不能只有不可点击的外键值 |
| 详情/编辑 | 信息字段集合保持一致；详情采用Descriptions或适当只读展示，编辑采用Form，不可编辑字段保持可见并标为只读；只读无需伪装为可输入，空值与不可用状态清楚区分 |
| 表单宽度 | 使用Form/Grid设置字段宽度和列数；短编号、日期、枚举不无条件撑满1440px，多行说明和图片按内容需要占宽；不给所有控件统一拍一个最大宽度，也不放任每页随意铺满 |
| 操作栏 | 按容器统一使用Modal/Drawer底部或页面表单操作区，取消为次操作、保存为主操作；与所属表单对齐、窄高窗口可达。页顶不重复另一组保存按钮 |
| 校验/提交 | 复用Form字段校验和错误定位；明确必填、帮助文字、服务端字段错误；提交中防重复，失败保留输入。状态变更与普通资料保存按业务边界分开 |
| 未保存离开 | 关闭、返回、切换对象时保护修改；保存成功后再离开，放弃需明确确认；不要在后台加载或保存失败后直接丢掉内容 |
| 图片 | 复用Upload的文件列表、预览、移除、进度和错误状态；通过业务适配接真实上传、暂存与保存关联，不手写第二套上传控件。按当前业务限制提示，不把原型开关当服务端授权 |
| 商品资料预览与生效提示 | 编辑预览标明“商品资料预览／未保存预览”；公开字段及空值沿用真实H5，不模拟完整NFC资格体验。已启用资料的保存提示说明下次成功读取生效，共用保存还要说明引用影响。详细目标规则及待审边界见[提案第2.4节](proposals/admin-make-rebuild.md#24-已同意的三层信息与字段展示)，本轮不改原型 |
| 反馈 | message/notification用于短反馈，Alert用于可操作的持续异常，Result用于整体结果；加载、空、失败、成功均有呈现。超时/结果未知提供核对路径，不能直接提示成功或自动重试高影响动作 |

## 4. 复用及例外

优先复用原始Make的应用壳、查询/列表/详情/编辑组合，以及Ant Design Layout、Menu、Table、Form、Descriptions、Modal、Drawer、Upload、Alert等官方组件。主题集中通过ConfigProvider与Token配置；布局使用现有样式工具，必要业务适配集中复用，不重写基础控件、不另造通用设计系统。

原稿组合能直接用时直接复用；需要改时先说明业务原因，再以官方示例或规范为依据调整。Ant Design组件保证单个控件的常规行为，页面宽度、信息层级、主次操作与业务流程仍须明确设计和验收。不能把“安装了antd”当作页面已经符合规范。

保留现有React/Vite/TypeScript工程和真实接口、安全规则；未经对齐不迁入Umi或替换页面框架。原稿模拟数据、假登录、自动写卡成功、上传开关、配置/诊断演示不进入正式业务。不同Ant Design/Pro组件版本的复用先核对实际兼容性，不能为使用示例引入冲突版本。

当前没有额外获批的视觉/交互例外。后续确需偏离时，在本节记录适用场景、原因、替代方案及批准依据，不把例外扩展成所有页面默认。

## 5. 后续需求怎样执行和验收

1. 开始管理端新需求先读本规范和对应产品规则，确认所用的是原始Make基准。先列业务场景、复用页面模式，以及拟改的入口、字段、步骤和容器；涉及偏离时说明依据。
2. 与cece对齐后才修改原型或业务页面；已批准范围内普通布局和实现细节由AI连续完成。若改变信息层级、主入口、主要容器或业务步骤，先重新对齐受影响部分，不先做一版再补解释。
3. 按批准顺序推进原型、产品、技术和代码；调用真实API后核对正常/失败/未知/未保存离开状态，检查列表返回、关联跳转和桌面矮窗口。对受影响页面进行实际视觉检查；构建通过不能替代外观与交互证据。
4. 交付说明实际复用了哪些框架/官方组件、必要定制原因、检查范围与剩余问题，由cece确认体验。只验证受影响场景，不反复扩大回归范围。
5. **React 19独立组件冒烟不再默认执行。** 如确有新增兼容性风险，AI先说明理由、范围和预计耗时，得到cece明确批准后再运行；不能借其他测试名称重跑同一矩阵。图片备份恢复生产门槛按原技术方案保留。

未来需求由[AGENTS](../AGENTS.md)要求先读本规范，并在[前端协作](FRONTEND_COLLABORATION.md)中落实；文档约束配合改前对齐、实际视觉核对和cece验收，不声称安装组件库或自动构建可以自动保证所有设计决策正确。
