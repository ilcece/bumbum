# BUMBUM 项目基线同步与自动检查

目的：让 AI 读取 GitHub 真实状态、恢复项目上下文，并按实际改动选择自动检查和复用有效证据，再继续产品与商业工作。第1–5节是只读基线同步，第6节说明正常工程中的 CI；不按工具名称分配固定角色，保留本文件路径供旧链接继续使用。

基线查询由 AI 执行，cece 不用逐条运行命令、维护脚本或搬运长报告。长期规则看[AGENTS](../AGENTS.md)，当前任务只看[TODO](../TODO.md)，历史证据看[CHANGELOG](../CHANGELOG.md)。[过度工程化复盘](PROJECT_PRIORITY_AND_OVERENGINEERING_REVIEW.md)的按需阅读条件统一见[AGENTS第0.5节](../AGENTS.md#05-创业目标优先先判断是否值得做)，不作为所有会话的固定前置阅读。

## 1. 使用现有连接，不再建设平台

优先用当前会话已有的GitHub连接器。确认它能按精确分支/提交读取完整文件、读取分支与开放PR列表并取得存在的后续页；只有搜索摘要或Library快照不足以完成同步。

连接器未提供或缺少能力时，优先使用当前环境已有GitHub CLI（gh）的只读API，不为同一能力维护重复Python工具、安装依赖或建立新Token。既有查询证据不能代替本轮工具能力；不同会话的连接器、版本及权限按实际核对，不从工具名称推断。

如果现有连接器和gh都无法完成某项必要读取，说明具体缺口和已覆盖范围，再判断是否值得增加最小辅助；不为未来假设建设授权签发、审计恢复或自动化管理平台。

基线同步不创建/删除远端分支，不写 PR，不触发 Actions，不部署。正常代码开发、提交、分支推送、PR 创建和经批准的合并继续遵守 AGENTS 第0、3节；第6节的 CI 说明不扩大这些授权，禁止直接向 main 推送，生产部署另行授权。

## 2. 开始会话时先读什么

同步触发频率统一按[AGENTS第1.1节](../AGENTS.md#11-基线报告的版本标识)。下面是完整同步的操作方法；同一任务的追问只按变化或依赖补查，提交/推送/合并前核对相关目标，不每次重跑整份手册。

1. 确认唯一仓库是 `ilcece/bumbum`，当前工具确实能读取它；不输出Token、密码、真实.env或完整认证环境。
2. 取得GitHub当前main的完整40位SHA；固定这个提交读取AGENTS.md、README.md、TODO.md，CHANGELOG.md只读最新相关记录，避免混用不同时间的文件；需追溯决策时再按任务关键词或具体事项查历史，不要求每次全文读取。
3. 有明确任务分支时再取它的完整HEAD，并读取对应任务文件和与main的差异；未指定时以main为基线。分支未推送或本地有未提交工作时单列本地状态，不冒充GitHub已经接收。
4. 分别读取远端分支与开放PR列表；按接口返回的下一页链接或工具游标继续，有下一页才读取，一页已完整即结束，不额外请求。不能因仓库小就忽略下一页，工具未能确认完整性时说明缺口。结合TODO发现活动分支，仅对任务分支和明确活动分支读取完整SHA并作必要比较；历史分支有状态疑问或独有工作时再深入，不随意删除。
5. 按当前任务补读PRODUCT、PRD、TECH_SPEC、API_CONTRACT、业务PRD或技术文档。查到足够上下文就回到当前主任务，不无差别重读全部历史。
6. 查询期间发现外部更新或目标变化时，复查相关提交和受影响内容；活动工作不明确时再完整发现分支/PR。分页不全或权限不足明确报告，不能用旧聊天或旧报告补齐，不机械要求每次结束都重查整份清单。

还在本地工作时，AI同时检查实际目录、分支、完整HEAD和未提交文件。以当前会话实际存在的仓库目录为准，不假定旧会话路径或Worktree仍可用；保护未提交修改，不擅自重建工作目录。若发现交付记录不符，保留现场先报告，不自行reset或覆盖。

GitHub只能展示已提交并推送的状态。未合入main的本轮规则不能当作远端main已有内容，也不为了“让新会话能看到”而擅自推送或合并。

## 3. 连接器不足时的gh只读参考

下面由AI按本次核对需要选用，不把示例顺序当作每次必跑清单。带示例名称、SHA或编号的位置需要替换，不为运行示例创建资源。每条请求都明确使用GET；不使用显示认证详情的参数，也不修改原有认证。

先确认身份、仓库和main：

```bash
gh api --method GET user --jq .login
gh api --method GET repos/ilcece/bumbum --jq '{full_name,default_branch}'
gh api --method GET repos/ilcece/bumbum/commits/main --jq .sha
```

### 第一步：发现活动工作

```bash
gh api --method GET --paginate 'repos/ilcece/bumbum/branches?per_page=100' \
  --jq '.[].name'

gh api --method GET --paginate 'repos/ilcece/bumbum/pulls?state=open&per_page=100' \
  --jq '.[] | {number,title,base:.base.ref,head:.head.ref,head_sha:.head.sha}'
```

上述--paginate选项只在接口返回下一页时继续；没有下一页，一次响应即完成该列表读取，不是强制多次调用。两个列表分别保证完整，结合TODO和任务确定活动分支；返回历史分支SHA不表示必须逐一分析，也不能仅凭名称认定为残留。

### 第二步：仅深入核对任务与活动分支

本次需要更新main或任务基线时，读取相应完整40位SHA；完整同步还核对明确活动分支。不能用短提交号或本地状态代替所需远端结果：

```bash
gh api --method GET 'repos/ilcece/bumbum/commits/指定任务分支' --jq .sha
```

分支名称中的特殊字符由AI按API要求编码。分支不存在或未推送就如实报告，不把本地HEAD填成远端结果。仅对当前任务及明确活动分支，用本轮读取的完整SHA比较：

```bash
gh api --method GET 'repos/ilcece/bumbum/compare/MAIN完整SHA...目标分支完整SHA' \
  --jq '{ahead_by,behind_by}'
```

ahead_by是目标分支尚未进入main历史的提交数，behind_by是main尚未进入目标分支历史的提交数。数量是历史关系，不直接表示业务文件遗漏；没有任务或活动分支时简要说明即可，本地未推送分支另行说明。

### 第三步：历史分支只做必要补查

对已有依据确认没有活动任务、开放PR或待处理独有工作的历史分支，仅简要记录，不逐一拉取完整SHA和比较。状态不明确或发现未合并工作时，再针对相关分支及PR深入核对；不随意删除历史分支。必要时查询PR合并状态：

```bash
gh api --method GET repos/ilcece/bumbum/pulls/25 \
  --jq '{number,state,merged,merged_at,head_sha:.head.sha,base_sha:.base.sha,merge_commit_sha}'
```

25是示例编号，先确认实际PR。closed不等于merged；不能只看PR标题、旧截图或“已关闭”就写成已合并。

按固定提交直接读取权威文件正文：

```bash
gh api --method GET -H 'Accept: application/vnd.github.raw+json' \
  'repos/ilcece/bumbum/contents/AGENTS.md?ref=MAIN完整SHA'
```

AI把MAIN完整SHA换成实际提交，按需替换文件路径。完整同步读取AGENTS、README、TODO及CHANGELOG最新相关记录；持续同一任务只补读变化或依赖内容，追溯时再查相关历史。任务分支的状态及相关文件使用其完整SHA，产品、接口、技术及数据文件按任务分层读取，不无差别读整个仓库。必要内容过大或接口返回不完整时说明缺口，不拿搜索片段替代。

## 4. 统一基线报告

用简短上下文摘要即可，实际版本核对与对外表达统一遵守AGENTS第1.1节。下面只是结构示例，不要求机械填满：

```text
当前任务：
版本说明：审核的是你提供的版本，分支没有更新（按实际结果填写）
结论与影响：
未覆盖范围或待决定事项：
下一步及负责人：
```

需要更新基线或检查远端目标时，实时核对完整提交和必要差异；列表有下一页才继续，一页完整就结束。只说明本轮实际覆盖范围，不将沿用记录说成刚刚现场核对。对外版本表达统一按AGENTS第1.1节，不重复罗列底层查询过程，也不为报告新增台账或生成器。

主任务和下一步负责人沿用TODO。涉及实现、验收、合并或部署时区分证据；未现场复核部署时标为最后已知状态，不因main已合并就断言服务器已更新，不为摘要罗列全部历史。

无需每次重跑历史测试、重新连接生产或要求cece重复验收；只有当前任务依赖新证据时才继续核对。报告完成后直接继续已授权的产品或商业工作。

## 5. 不完整时怎样处理

| 情况 | AI怎样处理 |
|---|---|
| 当前会话没有连接器 | 使用已有gh等只读能力；没有可用替代才说明具体缺口，不要求盲目重装插件 |
| 认证、网络或仓库读取失败 | 保留安全错误摘要，说明未读取范围，不索取或输出凭据，不修改认证 |
| 分页不完整或查询期间SHA变化 | 不宣称完整；重新做必要的只读核对，不能用旧报告补足 |
| 指定分支或文件尚未推送 | 分清远端已知与本地草稿，保护工作区，按已有交付授权处理；未授权不擅自推送或合并 |
| 状态只在历史记录中出现 | 标明证据日期和限制，不把旧测试、旧部署当作当前现场实测 |
| 有实现但无验收/合并/部署证据 | 分栏说明，不猜测已经完成 |

基线同步不负责写操作、授权签发或审计恢复。相关自动管理工具已停止建设并清理；正常工程授权及必要业务安全机制继续保留。

## 6. CI 分流与验证复用

先核对这次实际改了什么，再决定检查范围，不按文件数、改动行数或“小需求”名称减验。[项目检查工作流](../.github/workflows/checks.yml)运行 `python scripts/ci_scope.py`，由[分类脚本](../scripts/ci_scope.py)读取 GitHub 事件和基线，并检查提交范围的差异；文档白名单只在脚本维护，不在多份手册复制路径清单。文档规则与实际实现的语义一致性仍按[文档核对要求](../AGENTS.md#63-每次提交前的文档核对)人工审查。

| 真实变更范围 | 云端检查 |
|---|---|
| 所有改动均在文档白名单内 | 运行文档检查和本次提交范围的差异检查，不安装应用依赖、不构建双端，也不启动数据库或浏览器全量回归 |
| 任一改动不在白名单内 | 完整源码流程：基础检查、双端构建，以及隔离数据库和浏览器回归。认证或权限相关源码、依赖、测试、数据库、部署及 CI 自身变化均不能只因改动少就缩减 |
| 手动触发、未知事件或差异为空 | 保守走完整源码流程，不能将未知当作没有源码变化 |
| 正常 PR 或 push 的 SHA 无效、基线或差异范围不可得 | 按完整流程分类，同时使 `basic` 明确失败；先解决来源缺口，不能用别的提交范围冒充检查通过 |

分类使用事件对应的真实提交范围：PR 从目标分支与候选的共同祖先检查到候选提交，main push 对照推送前后提交；删除与重命名也核对旧路径，防止把删除源码后改名成 Markdown 误判为纯文档。缺少基线时先补齐必要提交，仍不能确定就明确失败。首次 push 的旧提交为全零时，从空树对照新提交并走完整流程。差异检查须检查这段提交范围，不能用干净工作区里空的 `git diff --check` 代替。

手动触发及未知事件没有可核对的 PR／push 范围，按完整流程执行，并明确只检查当前提交与父提交的差异；根提交使用空树。这种检查不称为已核对完整事件范围。

工作流保留 `basic`、`integration` 检查名，纯文档分流仍提供明确检查结果；不在顶层直接跳过整条工作流，以免必需检查一直等待。`gateway` 仍按既有 `include_gateway` 选项执行。纯文档检查通过只证明本轮文档检查通过，不能写成源码全量回归刚刚再次通过；是否实际启用分流，以对应 PR 或 main 的运行结果为准。

PR 重推可取消该 PR 的旧运行；main 不同提交独立运行，手动触发也与 push 分开。文档快路径不能取消前一个源码提交尚在运行的检查。

### 沿用证据与并行准备

已通过的验证可沿用，前提是本次依赖的被测内容、测试、锁定依赖和运行条件仍一致。比较实际内容，不只比较分支名或沿用旧聊天；仅补发布记录时，重查文档及真实差异即可，不重复构建、全量回归或实机验收。这里是交付证据复用，不是工作流跨运行缓存结果；非白名单变更仍走完整流程。源码、测试、依赖、构建或 CI 配置变化后，重验受影响部分并按上述范围运行云端检查；旧失败和新复验分别记录，不能用改过的断言或新结果改写旧 CI 结论。

本地先选能验证本次行为的定向检查，复用现有夹具、隔离环境及已核验产物；同一内容不例行安排本地、云端两套全量，需要定位失败时再按问题扩大范围。认证、安全或权限相关源码即使只有一行变化，完整源码 CI 和受影响的业务验证仍须保留；有真实设备要求时，自动回归不能替代该项人工确认。

源码 PR 的完整检查通过并合入后，main CI 可与已授权的构建、产物准备及只读发布预检并行。准备前仍须核对最终 main 与已通过检查的实际被测内容一致；树有变化、失败未解决或证据范围不明时，不能盲用旧树结果。正式切换前满足当次批准的发布条件，不能把并行准备解释成自动合并或生产部署授权。
