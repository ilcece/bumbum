# 手串 NFC 数字体验与权益探索

> 2026-11-02：cece已决定废弃旧祈愿 PRD，并授权整理复盘与文档调整。本文件记录方向重置及待验证问题，不是新 PRD，也不代表候选体验已获批准。当前任务、分支及下一步只维护在 [TODO](../TODO.md)。

## 1. 重新回答的问题

用户买到一条 BUMBUM 手串后，碰一碰应该获得什么，才能觉得这条手串更值得拥有、佩戴或长期保留？

先判断用户所得和实体联系，再决定打开什么页面。祈愿、情绪安放、数字作品、小世界、收藏、成长或产品权益都不能预先成为答案；不预设必须每天使用。当前只讨论普通手串使用者，不关联婚礼伴手礼；该机会具体需求另行讨论。

长期愿景仍见 [PRODUCT](../PRODUCT.md)。本文不提供候选功能的开发、部署、写芯片、改数据库或联系第三方授权；既有技术修复按其单独范围执行。以下访谈与试用内容是准备方案，尚未招募、开展或取得结果。

## 2. 两版体验与反馈证据

两版均为 Lovable 模拟 Demo。cece明确认为两版“没意思”；第二版仅获准独立模拟探索，没有据此修改正式 PRD。本文根据会话交接与反馈整理，不声称重新实测了两版 Demo，也不作为真实 NFC 或生产验收。

| 问题 | 第一版：每日一碰一签 | 第二版：表达—安放—回应—回望 | 产品判断 |
|---|---|---|---|
| 用户参与 | 默念、点击、领取通用福卡 | 选择四种意图，获得对应回应和可选小行动 | 动作主要决定领取或文案分类，没有形成用户在意的影响 |
| 仪式过程 | 触碰→默念→生成→收下 | 表达→安放→回应→回望 | 操作顺序完整，但尚未证明过程会产生感受 |
| 当次结果 | 一张祝福卡 | 更贴切、更温柔的回应 | 结果容易预料和替代，缺少值得期待的回报 |
| 再次使用 | 明天再领一张 | 回来标记“还在路上、有了变化、想留在这里” | 上次经历没有产生用户关心的后续，复访主要依靠规定或手动记账 |
| 长期积累 | 愿力与历史卡 | 心愿状态和回望记录 | 数据被保存不等于值得回看、珍藏或依恋 |
| 实体联系 | 手串打开领卡网页 | 手串打开情绪安放流程 | 更换成普通网页，主要内容仍成立，实体没有获得足够明确的新价值 |

第一版流程为模拟触碰→心中默念→点击→通用祝福卡→收下→愿力及历史。第二版四种意图为“愿有所成、愿心安定、愿人安好、记住此刻”。改善分类与文案没有证明核心吸引力改善。

根本问题是太早确定祈愿机制，再优化领取流程；用户收到什么被设计得很完整，为什么在意尚未成立。AI过早把方向带向情绪安放，未证明这符合使用者需求。不收集具体心愿时，系统不能声称理解并回应了具体心情。

以上是基于两版方案及cece反馈的诊断，不是广泛用户研究，不能推导所有用户都不需要数字祈愿。

## 3. 撤回的默认假设

- 手串有祝愿寓意，因此数字体验必须是祈愿或情绪安放。
- 用户需要每天触碰，日活是首要价值证明。
- 祝福文案和福卡足以成为核心回报。
- 愿力和历史数量增加，会自然形成收藏价值。
- 增加选择、温柔文案、动画或仪式步骤，就能补足参与感。
- 必须先建立持续使用机制，产品才有价值；低频但有实际价值的权益也应参与比较。

“这件信物有自己的小世界”“放灯后看它照亮哪里”等仅是会话提案，未获方向认可或开发授权，不能默认替代旧 PRD。

## 4. 旧规则如何处理

[旧 PRD](NFC_PRAYER_H5_PRD.md)原文保留，但整体退出当前需求依据；旧文档分支补充决定仅供追溯，不继续等待交互确认或合入。历史评审记录由本次方向重置替代，不改写过去发生的事实。

| 类别 | 规则 | 本轮处理 |
|---|---|---|
| 旧体验机制 | 每天一张、愿力累计、收下、回向、七天去重、节日优先、卡池与福卡分享 | 随旧方案退出当前需求，不机械迁入新体验 |
| 旧生成权限 | 当日认证、30分钟生成资格、跨日生成与重试口径 | 是福卡专属规则，不作为新业务默认权限；现有共用认证与接口不因文档调整改变 |
| 旧排期 | 11月底祈愿 MVP、12月种子反馈及依赖旧方案的后续成长 | 原交付内容失效；新范围、日期和验证方式待重评，不自动延期或承诺新日期 |
| 继续遵守的原则 | 芯片认证不等于所有权；最小化数据；保护认证秘密；真实反馈成功/失败；不承诺祈愿现实效果 | 保留，不因旧方案废弃而放宽 |
| 探索阶段沿用的边界 | 无个人账户、记录归信物、其他触碰者可能看到、不收集私密心愿 | 先尊重这些边界；若候选权益确需个人身份、私密记录或核销资格，单独说明必要性并评审，不默默改变 |

共用基础能力、服装主线及长期权益流转愿景保持原有范围与验收边界，不借本次重置新增工程工作。

## 5. 待比较的价值方向

下面三段可直接作为访谈材料，均是待验证候选，不是已选功能、已提供服务或对外权益承诺。先让用户判断具体所得，不制作 Demo，也不把三项合成一个产品。

| 候选及使用时机 | 触碰后具体得到什么 | 与手串的联系及先核实的问题 |
|---|---|---|
| 懂这条手串：买到时或养护前 | 看到这款手串的材料与工艺依据、佩戴和清洁方法；需要时重新查看对应说明 | 资料对应手中这款实物。先问用户最近是否确实查过这些信息，包装说明或普通网页是否已经足够；内容真实性和整理成本待核实 |
| 换绳与养护有着落：绳松、磨损或想维护时 | 找到适用的服务、联系渠道及受理条件；核对后知道可修什么、费用和怎样送修 | 解决这件实物的维护问题，低频使用也可以有价值。服务尚未开放；先核实用户现有维修办法、实际麻烦，以及品牌能否承担服务和成本；身份与核销另审 |
| 完成一件伴生作品：喜欢手串设计、想参与创作时 | 用这款手串的纹理或配色，通过几次选择完成一幅能看出本人选择差异的小作品；以后可继续调整同一作品 | 作品与具体款式有关，不靠通用祝福、每日任务或数量奖励。先问用户是否真想保存或继续；普通创作工具能否替代、素材与制作成本均待核实。沿用记录归信物、他人可能可见的探索边界，不收集私密文字 |

比较具体方案时，至少讲清：谁在什么情况下拿起手串、触碰后做什么、系统发生什么、用户获得什么、为什么不用普通网页替代，以及BUMBUM的内容或履约成本。

首次回报、再次触碰理由、长期保留价值分别验证，不能互相替代。若方案只适合低频使用，应按该使用周期判断价值，不强造每日任务。权益不得靠芯片认证直接推定所有权。

## 6. 这一轮怎样验证

建议 cece 先找3–5位实际购买或佩戴普通手串的人，每人聊约15分钟；这是小规模建议，不是已招募名单或通过门槛。婚礼机会及其宾客需求另行讨论，不混入本轮结论。

1. **先问经历，再介绍候选。**“你最近一次买或戴手串是为什么？”“最近有没有查过材质、养护、换绳，或想保留什么与它有关的东西？当时怎么解决？”记录实际例子，不先灌输数字收藏、祈愿或每日使用。
2. **逐段读第5节，允许全部不要。**每次换一下介绍顺序，说明均未提供。问：“你理解会得到什么？什么时候会用？现在什么办法能替代？哪一个值得继续聊，或都不需要？”不只问“喜欢吗”，也不以口头兴趣推定愿意付费。
3. **留最少证据。**在本文件已有反馈证据中汇总去身份的近期场景、现用办法、原话、选择或否决理由，以及愿意参与的下一步；区分实际行为、口头偏好和AI推测。不另建参与者台账，不记录无关个人资料，不把未发生的试用写成事实。

有具体使用场景、能复述所得，且愿意下一步用样品核对的候选，可以交 cece 判断是否做体验样例；这仍不等于市场需求成立或批准开发。若反馈只剩“好看、挺有趣”，或三项都缺实际使用理由，就先停下 Demo 和功能扩展，回到用户所得；服务能力或成本未核实的权益继续保持候选。若必须增加私人记录、个人身份或核销权限，先单独评审。

## 7. 真实样品试用另线推进

现有服装闭环可用于验证技术和办理是否可靠，入口沿用[生产实卡验收](DIGITAL_ITEM_ASSEMBLY_H5_ACCEPTANCE.md#生产实卡验收)，不复制另一套写卡或认领步骤。手串用户页目前仍不支持饰品资料展示，服装验收通过不代表手串新体验已上线。

先由AI整理待核对环境、实际发布版本、目标样品及现有权限，cece确认试用时点和对象。生产短信仍限指定验收号码；本轮已授权的代码修复不自动包含短信扩围、生产业务数据变更、发码认领或真实芯片写入。需要实际操作的部分，沿用其对应授权和验收边界。

获准后用少量专用样品走“碰卡看对物品 → 指定号码登录及交付码认领 → 从我的物品回访 → 后台核对同一物品及当前账户”。这会产生真实业务记录；目标环境或卡片不明确、短信准入未满足、物品不对应、出现归属异常或错误结果时，停止后续写入并保留不含秘密的错误编号，不反复重扫、重发或临时改库。

结果沿用既有验收清单和 CHANGELOG，记录实际环境、版本、样品引用、操作、观察及未验证项；本文件只汇总与手串价值有关的反馈。方向经 cece 认可后，再确定样例、成本、新PRD与最小技术范围。
