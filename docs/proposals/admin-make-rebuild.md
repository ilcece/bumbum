# 最新 Make 基准的后台重构：原型修改与后端缺口

本稿承接cece于2026-11-04本轮上传的《设计项目管理后台.zip》。先修改Make交互原型，由cece在Figma预览并迭代到满意，再整理涉及新增业务的技术方案，在现有任务分支整合。现有后端与分支保留，不删除、不先推倒重写。当前先整理业务定义、信息/功能架构和设计交互规范，与cece对齐具体改法后再改原型；cece随后明确授权按分支方案、以本次重新上传的原始Make制作高保真交互原型，确认无误后再构建正式代码。独立原型及离线交付件见第2.8节；不覆盖原始附件，不修改正式应用、接口、表结构或部署。

## 1. 已确认目标与本轮边界

- 页面框架、前端组件、视觉风格和交互体验尽可能沿用这份最新Make。需要修改的业务含义直接在原稿调整，不另做一套后台样式。附件中的规则文件只是外部参考，不替代仓库协作规范。
- 挂失、换新、转售要能接续新芯片；限定物品的数字身份与专属编号保留，例如限定T恤的`#001/100`在换新和转售后仍为同一号。替换实体不增加数字发行数量。
- 同持有人换新不改变所有权；转售必须换新实体及芯片并记录前后持有人。身份、实体、芯片、所有权分别记录，不能只覆盖芯片关联或复制旧芯片全部数据。
- 用户侧对外展示与内部记录分开。前任账号、联系方式、私人内容、申请证明及内部处理原因不自动转移或公开。
- cece已取消React 19独立组件冒烟的固定要求。后续按实际改动选择类型/构建和必要业务验证，不重复跑独立组件矩阵；如确有需要，先说明理由、范围和预计耗时，获cece明确批准后再执行。图片配套备份恢复的生产必要门槛保留。

物品归档、批量功能、真实支付/交易平台，以及B清理/C纠错的具体策略，不因Make中出现可点按钮就视为全部获批。具体资格证明、费用、可继承权益及履约异常仍待确认；已同意的交付核验后正式接续方向及自然年换新规则统一见[D接续提案](replacement-resale.md)。设计及通用交互只在[后台设计与交互规范](../ADMIN_UI_GUIDELINES.md)维护。

## 2. 原稿基准、信息架构及场景流程

### 2.1 信息架构与功能职责

六个业务对象已确认：数字物品身份、实体载体、芯片、持有人、操作记录、数字权益。概念边界见[产品愿景](../../PRODUCT.md#3-统一概念账户数字藏品实体载体和芯片)，权益详细规则见D提案。对象不必各建一个一级菜单，避免把数据模型直接照搬为导航。

| 工作区 | 管理员关心的信息与功能 | 当前边界 |
|---|---|---|
| 登录与会话 | 账号/密码/TOTP、会话恢复、失败反馈、运行状态、退出 | 复用真实认证；账号创建/重置仍走受控管理流程 |
| 工作台 | 库存、待处理提示、真实触碰统计和快捷定位 | 复用已交付查询，不伪造待办数量 |
| 芯片管理 | 登记、批次、状态、首次来源、绑定物品引用、配卡与核验 | 身份/硬件操作归芯片；关联链接进入物品详情；停用/挂失/退役和专用纠错仍有后端缺口 |
| 物品管理 | 稳定身份/发行编号、资料、当前实体与芯片、持有人、数字权益、历史 | 现行普通维护复用；独立实体/所有权/权益模型尚未交付，不在详情顶部堆完整履约流程 |
| 款式/发行资料 | 共用尺码表、允许尺码、颜色与发行约定 | 先明确资料维护职责，入口设于物品管理“款式与发行资料”，不增加一级菜单 |
| 业务处理 | 挂失保护、换新申请与准备/交付/接续、后台转售 | 从对应信息分区进入同一处理流程，复杂流程建议独立处理界面；布局须先审核 |
| 维护、清理与纠错 | 废弃数据资格/引用检查、专用纠错、处理结果与操作历史 | B/C独立审核，不靠普通编辑或本地删除按钮替代 |
| 操作历史/系统状态 | 查询操作人、对象、动作与结果，定位故障 | 当前仅部分审计写入及运行检查；完整日志查询接口未交付 |

用户侧只提供约定的数字内容/权益及流转信息查看，本期不开放发起转售入口；前任身份与私人资料按权限隔离。原稿未被App导入的页面不能作为现有导航或已交付能力。

### 2.2 按实际场景梳理流程

下表覆盖当前后台重构相关场景；不替代A/B/C/D对输入、资格及异常的逐项定义。正常维护已有能力和提议能力必须分别接入，不能用原型可点击代替业务交付。

| 场景 | 管理员操作路径及关键结果 | 需保留的边界 |
|---|---|---|
| 登录/恢复/退出 | 打开后台 → 核对账号、密码、当前TOTP → 登录 → 到期或退出后回到登录 | 错误反馈、真实会话/CSRF和安全退出；不复制假登录及预填凭据 |
| 芯片登记/连续登记 | 扫描或输入UID → 重复核对 → 填写批次及验证标记 → 保存 → 查看确切新记录或继续登记 | UID冲突不重复造卡，失败保留输入；首次来源与批次如实记录，项目只从关联物品读取 |
| 创建物品/连续创建 | 维护共用款式资料 → 创建物品选择项目、业务编号和款式引用 → 保存关联 → 查看或继续 | 未知结果先核对确切对象，取消不改变已保存图片；不复制本地顺延号逻辑 |
| 首次绑定与配卡 | 从芯片核对物品引用 → 首次绑定 → 受控密钥/写卡 → 配置核验 → 查看结果 | 真实卡核验不以勾选代替；当前唯一关联约束保留 |
| 查询与关联查看 | 筛选查询 → 打开详情 → 点关联芯片/物品 → 返回原查询上下文 | 已生效条件、分页及来源恢复；不只依赖页面保活 |
| 查看/编辑资料 | 详情核对 → 修改允许字段/图片 → 校验并保存 → 返回同对象 | 同字段只读/编辑；状态独立操作；失败、关闭和离开保护 |
| 临时停用/恢复 | 从芯片状态分区核对影响 → 确认动作 → 查看真实结果/历史 | 不等于挂失/退役；操作API及恢复资格未交付 |
| 废弃芯片删除 | 查到目标 → 核对是否确属可清理数据及引用/配置/关联 → 展示影响 → 按B规则确认 → 核对结果 | 未定义资格前不开放删除；生产/已配置/有历史对象不因“废弃”直接物理删除；符合条件的专属验证数据按B定稿处理 |
| 废弃物品处理 | 核对关联芯片、媒体、历史及清理资格 → 区分清理与退出 → 确认处理 | 不借删除抹掉真实流转/审计；编号复用与统计政策由B定义 |
| 录错纠正 | 核对项目/编号/绑定事实 → 区分未配置与已配置 → 专用C流程 → 核对前后结果 | 不用普通PATCH改稳定身份，不绕过已配置卡的保护 |
| 挂失/解除 | 核对申请人及当前实体 → 明确阻断范围 → 确认挂失；找回后另核对解除条件 | 不自动扣换新次数；已退役不可普通恢复 |
| 定期/挂失换新 | 核对持有人及额度 → 目标尺码/颜色规则 → 准备候选新实体/卡并核验 → 交付 → 管理员核验后正式接续 | 同持有人、编号不变、共享年度额度、旧实体不回收；跨年办理及扣减时点待定 |
| 后台转售 | 核对前后持有人及权益 → 明确冻结 → 准备新实体/卡 → 交付核验 → 正式变更归属和授权 → 查看历史 | 旧实体保留；不扣或重置换新额度；用户仅查看流转摘要 |
| 处理失败/取消/争议 | 按准备/运输/接续阶段核对实际结果 → 决定继续、取消或专门处置 → 保留记录 | 不盲重试正式切换，不自动复活旧卡；异常政策须定稿 |

### 2.3 先对齐再修改

展示基准始终是cece原始最新版压缩包，具体尺寸、分区、控件及状态见统一规范。cece已整体认可现有页面改动方向、挂失/换新/转售及发行资料审核图，并授权细化字段展示和实体术语；按本节及第2.4节更新独立审核图。后续如改变已同意的主入口、主要容器或业务步骤，仍先对齐受影响部分，不为普通字段排版重走整套审批。

### 2.4 已同意的三层信息与字段展示

cece已认可页面整体方向，并同意细化字段、界面用“实体”替代“载体”，明确区分以下三层；第一层内部再分开可维护的款式通用内容与发行时的约定。此区分不增加一级菜单，也不代表现有数据库已完成分层或新增普通编辑权限。

| 信息层 | 管理什么 | 页面与维护位置 |
|---|---|---|
| 第一层：款式通用资料 | 款式编号、名称、设计介绍、材质说明、通用养护/寓意、参考图片、尺码表与可选尺码 | 物品管理“款式与发行资料”维护；统一维护、同步引用，保存提示影响范围；独立于发行承诺和实体事实 |
| 第一层：某次发行约定 | 发行系列/批次、总量、限定规则、允许颜色和例外、权益承诺 | 物品关联当次适用的发行约定；已发行承诺不可被日常商品资料保存追溯修改；同款再次发行可有不同约定 |
| 每件数字物品身份 | 唯一物品编号、项目、限定序号、当前持有人及归属历史、权益使用情况；关联共用款式及发行记录 | 物品详情为核对入口；编号与归属不能通过普通编辑修改，权益通过专用办理更新 |
| 每次交付的真实实体信息 | 实体记录、交付次序、实际尺码/颜色、关联芯片、准备/交付/接续/退出记录 | “当前实体与历史实体”分区；换新申请选择目标尺码，转售在新实体准备记录本次交付尺码；新交付写新记录，旧记录保留 |

**已确认的目标关系：** cece明确“共用资料统一维护并同步引用；实体交付信息独立保留”，替代此前逐件保存的目标方案。cece本轮进一步明确款式与发行约定分工；沿用已确认的共用同步关系，物品只关联款式，不复制名称、介绍、材质、养护/寓意与图片；维护同一款式后所有引用物品同步展示，保存前明确影响范围。每次实体的实际尺码、颜色、芯片和交付历史独立保留，不随共用资料保存回写。

**现有实现与实施边界：** 正式应用仍按物品存储资料，款式编号仍是可空/可重复文字；本轮只在隔离原型演示引用关系。正式重构前需补审款式/发行关联、既有同码不同资料的冲突归并、图片归属与删除引用/配套备份恢复、事务和查询契约；禁止直接按字符串批量合并历史。芯片的项目改为从关联物品读取：登记不填、芯片不独立维护，只在芯片列表/详情展示并支持筛选，未关联显示“未关联物品”；实际后端仍保留原项目字段，迁移、密钥项目语境及历史查询需技术方案核对，不在本轮改表。

**录入与维护路径：** 先从物品管理“款式与发行资料”新建共用款式（款式编号、项目、名称必填，其余资料按适用字段维护）；再建物品草稿，选择已有款式，或在草稿详情“维护身份关联”补关联。发行记录负责发行名称、总量和不可追改的发行约定；本件限定序号与发行总量组合显示，例如序号1/总量100展示为#001/100，不替代系统物品编号。编号范围尚待cece确认“每款每次发行”或“整个系列跨款式”，本轮已有单款发行样例仅用于展示，新发行保存与新编号分配暂不开放。原型仅允许未绑定、未归属的草稿维护款式关联，已发行身份的变更不通过普通资料保存绕开C纠错。

**生产验证标识：** 芯片登记、未配置且无关联历史芯片的维护，以及物品草稿创建可演示标记与筛选；标记不授予删除/退出/释放关联资格。已有配置或关联的芯片标记只读并显示原因，补标/转正式与清理权限仍按B技术方案另审。

| 物品详情分区 | 具体字段及操作 | 普通资料编辑态 |
|---|---|---|
| 基本信息 | 物品编号、项目、资料状态、创建/更新时间；计划增加发行系列、限定编号、当前持有人、首次绑定所有人时间 | 同字段只读展示；“首次绑定所有人”不同于首次绑定芯片。资料状态不等于芯片或权益状态 |
| 日常维护 | 编辑资料入口、按条件提供的独立启用/停用；不另建一套款式/状态/验证标识表单 | 不重复呈现另一组保存按钮；启停不混入资料保存，验证标识仍按B提案定稿 |
| 商品资料 | 款式编号、名称、介绍、材质、养护说明、图片、尺码表；共用资料引用 | 目标原型在共用款式维护适用资料；尺码表/可选尺码按需展开，不在挂失中突出。正式应用尚未迁移，原有编辑权限见第2.5节 |
| 当前实体与历史实体 | 当前实体记录与交付次序、实际尺码/颜色、芯片引用/状态、密钥生成与配置核验摘要、正式接续时间；历次实体的对应事实与退出原因 | 全部只读；挂失靠近当前芯片，换新从数字权益进入。不得在普通保存中覆盖旧实体历史 |
| 数字权益与办理记录 | 换新年度、剩余次数、约定规则、进行中/历史办理记录、转售说明 | 同字段只读；申请换新/后台转售进入独立流程，不将按钮状态当已交付接口 |
| 所有权流转记录 | 当前及历任持有人、起止/变更时间和办理引用 | 全部只读；同持有人换新不伪造一次所有权转移，用户摘要按隐私规则另展示 |

详情与编辑保留相同适用字段。编辑中只读关联和历史可用描述列表/可展开分组，不能省略数字身份或把历史当可编辑表单；用户视角预览仅展示允许公开的商品资料，不展示后台持有人、资格证据或内部历史。

#### 后台业务表字段与引用（整理稿）

这里的“表”指按业务职责整理的信息表，不是数据库建表方案，也不要求每张表都有一级菜单。它承接已确认对象和三层分工，供核对字段与页面；拟新增字段的必填条件、状态枚举、权限和技术存储仍需在对应业务/技术方案定稿后实施。项目沿用现有服装/饰品分类，不另扩展项目管理功能。

**字段阅读约定：** “引用”表示选取另一份已有记录，不重复录入其名称或资料；“系统生成/计算”不是管理员可随意输入的字段。下列业务表都应能识别具体记录及必要创建/更新时间，时间和历史不能用普通表单改写。联系方式、资格证明及内部记录按权限保护，不默认公开。

| 业务表 | 用途及后台入口 | 关联概览 |
|---|---|---|
| 款式资料 | 维护同款共用商品内容；物品管理内“款式与发行资料” | 一个款式可有多次发行、被多件物品引用 |
| 发行约定 | 保存某次发行的限定与权益承诺；与款式资料同一工作区分开维护 | 引用款式及适用权益规则；多件物品适用同次发行 |
| 数字物品 | 保存每一件稳定数字身份；物品管理 | 引用款式、发行；关联实体、持有人、权益和办理历史 |
| 实体交付 | 保存每次真实交付事实；物品详情及办理过程 | 每条属于一件数字物品，并记录本次芯片；一件物品可有多次交付 |
| 芯片 | 登记、配置、核验和服务状态；芯片管理 | 经关联实体/物品追溯身份；项目只从关联物品读取 |
| 持有人 | 识别当前/接收账户；从物品和办理引用查看 | 一个账户可持有多件物品；不另造物品专属账户 |
| 权益规则 | 说明某次发行提供什么权益；发行约定内查看 | 一次发行可适用多项权益；定期/挂失换新共享同一年度额度规则 |
| 年度权益记录 | 记录某件物品某年的实际额度使用；物品权益分区 | 引用数字物品、适用规则和使用它的办理记录；不归属某个人重算 |
| 业务办理 | 记录申请、准备、交付与接续；从物品相应分区进入 | 引用物品、申请时持有人、接收人、权益及新旧实体/芯片 |
| 所有权流转 | 保留历任持有人和转移事实；物品流转分区 | 引用物品、前后账户及对应办理；从成功业务产生，不手工录一份结果 |

**1. 款式资料表**

**关键引用链与改动影响**

- 款式 → 多次发行；数字物品 → 款式＋适用发行。引用的款式、发行与物品项目必须一致，具体编号分配范围仍待确认。
- 数字物品 → 多次实体交付 → 每次芯片；当前实体/芯片由正式接续结果识别，不能按最新创建时间或最新发货记录猜测。
- 数字物品 → 当前/历任持有人；流转记录引用前后账户与办理事实。碰卡查看、芯片绑定与所有权确认是不同业务。
- 发行 → 权益规则；数字物品＋自然年＋共享额度规则 → 年度使用记录 → 办理。转售变持有人，不重建同年度额度。
- 共用款式修改影响其所有引用物品的通用展示；发行承诺、实体交付、年度使用与所有权历史独立保存，不能被普通资料保存级联改写。

现有正式后台仍是按件商品资料、芯片/物品登记查询及部分配置能力；完整款式/发行、独立实体、所有权/数字权益/办理服务尚未交付。已有用户/所有权等预留表也不等于业务已可用。此整理稿不修改现有数据库、接口或原型，拟议字段在技术实施前按第2.5节及后端缺口核对。

#### 资料保存、展示与生效（新增细则待审）

下列内容补齐目标行为，不表示正式后台、原型与H5均已实现；本轮只整理规则。三层分工、款式与发行约定分开及共用同步关系沿用cece已确认内容；下面新增的生效、提示和适用版本细则供审核。

**取值与影响范围**

- 款式资料服务于通用内容维护；发行约定表达当次发行的承诺。同款再发行可引用新的发行约定，原有数字物品保留当时适用的约定及其可追溯版本，不随新批次或通用介绍修改而改变。具体版本标识和保存方式在技术方案确定，不为此建设通用发布平台。已发行约定的事实纠错另审，不能用“修改文案”绕开。
- 发行颜色、总量、限定规则与权益来源于适用的发行记录；实际尺码、颜色、芯片与交付/退出时间来源于对应实体记录。未维护的发行颜色明确显示未记录，不借用当前实体颜色代填。上一轮原型已分开这两种颜色的取值来源。
- 共用保存影响所有引用该款式的数字物品，包括已有多次发行的物品；确认提示列出引用总数、其中已启用的数量及受影响的内容范围。更新仅作用于共用商品资料，不改变各自发行承诺、启停状态、身份、持有人、权益使用或实体历史。新增/修改某个引用不授予更改已发行身份的权限。
- 必要的单件展示差异须先明确具体字段和使用场景，再单独审核；本期不额外引入“共用默认值＋单件覆盖＋批量同步”的混合维护机制。

**预览与用户视图**

| 场景 | 规则 |
|---|---|
| 编辑中的右侧预览 | 名称为“商品资料预览”，标明“未保存预览”；使用当前表单和暂存图片，不等于用户已读取的新资料，不证明真实上传服务已启用 |
| 保存后的用户视图 | 使用已成功保存且通过查看资格检查的数据；公开字段、空值/无图处理与真实H5一致，不能直接把后台Descriptions作为用户页，也不把后台“未填写”提示自动搬给用户 |
| 内部信息 | 服务端按用户接口的允许字段返回，排除后台持有人账号、证明、内部原因和完整历史；不能只依赖前端隐藏。已有公开认领标识不等于公开持有人身份 |
| 当前实体 | 只展示已正式接续的当前实体。申请选择L码、原实体为M码时，准备/运输/收到阶段仍显示M码；若以后展示办理进度，另列“新实体准备中”，不覆盖当前事实 |
| 流转摘要 | 按D提案另定允许公开的事件、字段和时间粒度，再由服务端提供；不直接返回后台完整历史，当前不因原型存在记录就开放完整用户流转页面 |

商品资料预览仅核对公开内容和排版，不承担NFC真伪验证、停用、资格撤销、图片受控读取及整个用户体验的验收。对应行为仍按[服装触碰规范](../product/fashion-touch.md#2-手机资料页与持续查看)及接口契约验证。

**保存与启停：沿用简单生效方式**

不增加“编辑新版但线上仍显示旧版”的独立草稿或发布操作；物品草稿状态与待发布内容版本不是同一概念。

| 操作 | 用户侧影响 |
|---|---|
| 保存草稿或停用物品的资料 | 只保存内容，不自动启用或取得查看资格；原先不可查看的状态不因保存而改变 |
| 启用物品 | 仅改变启用状态；仍须通过芯片绑定、配置、防伪及有效查看资格等现行检查，不承诺启用后任何人都能查看 |
| 保存已启用物品资料 | 成功提交后，新资料在用户下次成功向服务端读取时生效；失败/结果未知不提前报生效。共用保存时，适用于每件已启用的引用物品，不限于当前打开的一件 |
| 停用物品 | 后续验证与资料读取按现行规则阻断；已打开页面在后续状态检查时按H5规范处理，不承诺远程立即抹除已取得内容；不表示挂失、退役或转移权益 |
| 正式换新/转售接续 | 核验交付后明确切换当前实体和芯片授权，必要时变更持有人；独立于商品资料保存和启停，不因编辑预览、保存或启用提前切换 |

“下次成功读取”包括现有H5的前台每60秒更新、切回立即更新及整页刷新；本轮不改变其频率、资格检查和失败反馈，也不新增实时推送。停用、失效及读取失败时的旧内容处理遵循H5规范，不能把旧副本当最新数据。保存按钮附近提示“保存后，更新内容将在用户下次成功读取资料时生效”；共用保存同时说明所有受影响的引用对象。

名称建议将界面“资料状态”统一为“物品启用状态”，字段仍为item.status，草稿/启用/停用及预留归档含义不变。此名称待cece确认后再统一调整列表、详情、表单、筛选和提示，本轮不修改原型或接口；不将内容保存称为“发布”。

### 2.5 当前录入字段与未来字段的区别

## 2A. 历史首轮演示记录（不作为下一轮设计基准）

此前AI提前修改的首轮原型并未获得页面改法确认，其在物品详情顶部放置生命周期操作区的做法已被cece否定。以下保留为历史说明和交付限制，不作为已批准入口/步骤；下一轮从原始Make及第2节重新对齐，不继续沿用该改稿。

### 2A.1 操作入口

历史首轮曾建议以**数字物品详情**作为挂失、换新、转售的主入口。它承载稳定身份、限定编号、当前持有人和历次实体；管理员从这里能看到一次业务会影响什么。

芯片页保留登记、批次、配卡核验、硬件状态及关联查询。芯片页发现损坏/丢失时，跳到对应物品处理同一流程，避免芯片、物品两个页面各维护一套换新逻辑。未配置的误绑定仍归专用纠错，不能混成所有权转移。

首轮保留最新Make的侧栏、顶栏、列表、详情抽屉与表单样式，新增“物品身份、载体与流转”区；重复的可见挂失/接续入口统一到该区。其它原稿页面尚未逐项重做。

### 2A.2 限定身份、实体与所有权

| 对象 | 限定T恤示例 | 换新 | 转售 |
|---|---|---|---|
| 稳定数字身份 | 数字物品编号＋发行系列＋`#001/100` | 保留 | 保留 |
| 实体载体 | 第一件T恤及其实体编号 | 新增第二件，保留第一件历史 | 新增交付给接收人的实体，保留旧实体历史 |
| 当前芯片 | 当前实体上的认证入口 | 接续新芯片，旧卡退役 | 接续新芯片，旧卡退役 |
| 当前持有人 | 示例持有人甲 | 保持甲 | 变为示例持有人乙，记录甲→乙 |
| 历史与隐私 | 载体轨迹、归属变化、内部证据 | 保留必要历史 | 保留必要历史，前任私人信息不随物品公开 |

限定编号须在对应发行系列内解释，不能取代系统唯一物品编号；普通非限定物品不强行补`#001/100`。当前已确认尺码可调整、颜色按发行约定限制；旧演示未完整表达，具体规则统一见D提案。

### 2A.3 演示步骤

- **挂失：** 核对申请与当前物品 → 确认冻结范围；保留数字身份、限定编号和持有人，当前载体挂失。挂失本身不立即换卡或删除历史。
- **换新：** 核对申请/现持有人 → 准备新实体及新芯片 → 对照前后信息确认接续；持有人不变，实体代次增加，旧卡退役。
- **转售：** 核对原持有人与另一位接收人 → 准备新实体及新芯片 → 确认接续与所有权变更；记录前后账号，身份/限定编号保持不变。
- **用户侧预览：** 以公开档案视角查看作品、限定编号、服务状态与流转摘要；不显示管理员可见的账号、手机号、内部原因。

新增限定T恤和三位持有人均为合成样例。步骤中的资格和准备确认只演示界面，不是正式核验方式；真实版本不能用复选框代替持有人资格证明或实卡核验，也不能点击“下一步”就自动生成密钥、视为写卡完成。公开流转次数/摘要属于首轮展示提案，尚不是最终披露政策。

首轮Figma副本：[BUMBUM后台 · Make改稿01](https://www.figma.com/make/UooGXZe3IW8vHOZGcSUYJ6)。**当前仅创建了空白副本，源码上传被云端代理CONNECT 403拒绝，尚未导入，不能作为可运行预览。** 修改包及本地截图随本轮交付；上传失败后未继续导入或盲重试。环境状态显示网络不限域名，具体代理拒绝原因未确认，不能归因于Make模型额度。导入、预览和人工结论分别记录。当前连接支持向新空白Make导入项目，不支持反复覆盖已填充文件；后续每轮提供独立副本并保留上一版。

### 3.3 原稿中不能照搬的实现假设

原Make的换卡函数直接设置新芯片keys_generated、provisioned_at和last_counter；转售并未更新owner_account_id，也没有限定编号或独立实体记录。挂失只改变数组，却提示真实凭证已立即失效。首轮统一流程补了演示字段、前后归属和准备阶段，真正效果仍须由后端实现证明。

原稿用本地数组过滤、分页和顺延编号，部分字段名/状态与现有API不同；图片使用本地/模拟资产。架构整合时保留这些页面组织与外观，通过适配接真实服务，不复制模拟存储、身份与密码到正式工程。

未被App导入的WorkflowGovernancePage仍在附件源码中，不能据这个未展示文件宣称已有独立治理页面。当前主要入口位于芯片、物品详情及日志页。
