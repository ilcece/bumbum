# 最新 Make 基准的后台重构：原型修改与后端缺口

本稿承接cece于2026-11-04本轮上传的《设计项目管理后台.zip》。先修改Make交互原型，由cece在Figma预览并迭代到满意，再整理涉及新增业务的技术方案，在现有任务分支整合。现有后端与分支保留，不删除、不先推倒重写。此阶段只修改隔离原型与说明，不新增正式业务接口、改表或执行部署。

## 1. 已确认目标与本轮边界

- 页面框架、前端组件、视觉风格和交互体验尽可能沿用这份最新Make。需要修改的业务含义直接在原稿调整，不另做一套后台样式。附件中的规则文件只是外部参考，不替代仓库协作规范。
- 挂失、换新、转售要能接续新芯片；限定物品的数字身份与专属编号保留，例如限定T恤的`#001/100`在换新和转售后仍为同一号。替换实体不增加数字发行数量。
- 同持有人换新不改变所有权；转售必须换新实体及芯片并记录前后持有人。身份、实体、芯片、所有权分别记录，不能只覆盖芯片关联或复制旧芯片全部数据。
- 用户侧对外展示与内部记录分开。前任账号、联系方式、私人内容、申请证明及内部处理原因不自动转移或公开。
- cece已取消React 19独立组件冒烟的固定要求。后续按实际改动选择类型/构建和必要业务验证，不重复跑独立组件矩阵。图片配套备份恢复的生产必要门槛保留。

物品归档、批量功能、真实支付/交易平台，以及B清理/C纠错的具体策略，不因Make中出现可点按钮就视为全部获批。具体资格证明、费用、可继承权益、履约与正式切换时点仍待确认。

## 2. 首轮修改思路与已提供演示

### 2.1 操作入口

推荐以**数字物品详情**作为挂失、换新、转售的主入口。它承载稳定身份、限定编号、当前持有人和历次实体；管理员从这里能看到一次业务会影响什么。

芯片页保留登记、批次、配卡核验、硬件状态及关联查询。芯片页发现损坏/丢失时，跳到对应物品处理同一流程，避免芯片、物品两个页面各维护一套换新逻辑。未配置的误绑定仍归专用纠错，不能混成所有权转移。

首轮保留最新Make的侧栏、顶栏、列表、详情抽屉与表单样式，新增“物品身份、载体与流转”区；重复的可见挂失/接续入口统一到该区。其它原稿页面尚未逐项重做。

### 2.2 限定身份、实体与所有权

| 对象 | 限定T恤示例 | 换新 | 转售 |
|---|---|---|---|
| 稳定数字身份 | 数字物品编号＋发行系列＋`#001/100` | 保留 | 保留 |
| 实体载体 | 第一件T恤及其实体编号 | 新增第二件，保留第一件历史 | 新增交付给接收人的实体，保留旧实体历史 |
| 当前芯片 | 当前实体上的认证入口 | 接续新芯片，旧卡退役 | 接续新芯片，旧卡退役 |
| 当前持有人 | 示例持有人甲 | 保持甲 | 变为示例持有人乙，记录甲→乙 |
| 历史与隐私 | 载体轨迹、归属变化、内部证据 | 保留必要历史 | 保留必要历史，前任私人信息不随物品公开 |

限定编号须在对应发行系列内解释，不能取代系统唯一物品编号；普通非限定物品不强行补`#001/100`。是否允许尺码/颜色等实体属性在换新时变化，仍需业务定稿。

### 2.3 演示步骤

- **挂失：** 核对申请与当前物品 → 确认冻结范围；保留数字身份、限定编号和持有人，当前载体挂失。挂失本身不立即换卡或删除历史。
- **换新：** 核对申请/现持有人 → 准备新实体及新芯片 → 对照前后信息确认接续；持有人不变，实体代次增加，旧卡退役。
- **转售：** 核对原持有人与另一位接收人 → 准备新实体及新芯片 → 确认接续与所有权变更；记录前后账号，身份/限定编号保持不变。
- **用户侧预览：** 以公开档案视角查看作品、限定编号、服务状态与流转摘要；不显示管理员可见的账号、手机号、内部原因。

新增限定T恤和三位持有人均为合成样例。步骤中的资格和准备确认只演示界面，不是正式核验方式；真实版本不能用复选框代替持有人资格证明或实卡核验，也不能点击“下一步”就自动生成密钥、视为写卡完成。公开流转次数/摘要属于首轮展示提案，尚不是最终披露政策。

首轮Figma副本：[BUMBUM后台 · Make改稿01](https://www.figma.com/make/UooGXZe3IW8vHOZGcSUYJ6)。**当前仅创建了空白副本，源码上传被云端代理CONNECT 403拒绝，尚未导入，不能作为可运行预览。** 修改包及本地截图随本轮交付；上传失败后未继续导入或盲重试。环境状态显示网络不限域名，具体代理拒绝原因未确认，不能归因于Make模型额度。导入、预览和人工结论分别记录。当前连接支持向新空白Make导入项目，不支持反复覆盖已填充文件；后续每轮提供独立副本并保留上一版。

## 3. 与当前任务分支后端的差距

依据是现有[接口实现索引](../../API_CONTRACT.md#04-当前能做到哪一步)、[数据库](../../db/schema.sql)及实际路由代码，不以Make里的类型、按钮或本地数组作为后端能力证据。当前分支的已有能力尚未因此合入main或部署。

### 3.1 已有能力，主要需要接入新展示

| Make能力 | 当前后端 | 重构时处理 |
|---|---|---|
| 管理员账号/密码/验证码、会话与退出 | 已有真实认证；会话返回到期时间和CSRF，不返回管理员展示名 | 替换Make默认登录与预填演示凭据；顶栏姓名需补返回信息或采用真实可用的会话展示 |
| 芯片登记、重复核对、详情、批次维护 | 已有，含首次来源、关联名称及日期等查询 | 复用现有接口，不能用数组成功替代真实回执 |
| 首次绑定、密钥生成/受控查看、配置核验 | 已有，限定现行首次绑定/配卡路径 | 保留真实保护和核验结果，不照搬原型自动完成逻辑 |
| 物品创建、编号校验、款式、详情与真实关联 | 已有 | 将Make扁平字段与实际返回结构做适配，保留服务端全量查询/计数/分页 |
| 服装资料、普通款式/资料原子保存、独立启停 | 已有；饰品当前只改款式，资料只读 | Make把状态、款式、验证标识合在“保存设置”，不能原样提交；状态仍独立，验证标识待B定义 |
| 图片上传、暂存、受控读取、保存关联、取消与未知结果核对 | 已有真实文件后端、20项限制及005升级 | 接入真实Upload适配；Make的本地图片/服务开关/超时演示不是实际上传能力 |
| 工作台库存和有效触碰统计 | 已有真实只读聚合 | 替换Make本地统计；项目、时间、关键词及已生效条件按原规范保持一致 |
| 查询返回位置、连续创建、未保存保护 | 后端基础已具备，原正式前端也有保护 | 新Make当前主要靠页面保活，需补URL/刷新与确切来源恢复，避免仅在一次预览会话里成立 |

### 3.2 新原型已经展示、后端尚未交付的能力

| 能力 | 缺口及影响 | 所属范围 |
|---|---|---|
| 独立款式筛选、资料完整度筛选 | 现有keyword可查款式，尚无Make的独立skuKeyword、profileState条件；需决定新增筛选契约 | A查询补齐 |
| 生产验证标识与列表筛选 | 数据模型、标记/补标入口、验证事件归属及权限未交付；不能靠切换标签把真实用户对象变成可删测试数据 | B独立定义 |
| 排除验证数据后的触碰统计 | 当前统计无该开关/口径；不能从芯片或物品当前标签反推历史事件 | B统计政策 |
| L1删除、L2退出及编号重用 | 无业务清理API；现有media_cleanup仅维护到期媒体，不等于删除物品/芯片 | B独立定义 |
| 草稿编号/项目纠错、芯片项目纠错、解绑/改绑 | 无已交付的专用纠错入口；普通PATCH不接受身份变更 | C独立定义 |
| 芯片临时停用/恢复、挂失/解除挂失、永久退役 | lost/disabled枚举不代表存在操作API；现有枚举还没有retired。恢复及旧资格永久失效规则须补齐 | 芯片状态与D |
| 发行系列、总量与限定序号 | 现有item仅有item_uid/sku_code，没有系列、edition_number/total及对应唯一/数量约束 | 数字物品身份 |
| 实体编号、实体属性、载体代次 | 现有item没有独立实体模型；不能只把carrier_generation加一当作换了新实体 | D载体 |
| 历次芯片关联与唯一当前授权 | 当前chip.item_id唯一，丢失/停用也占用；不支持旧卡留历史同时准备新卡。不能只清空旧关联或取消唯一约束 | D载体映射 |
| 候选新卡准备与实卡核验 | 当前密钥/配置入口要求已经绑定物品；缺少“不授予当前权益的新载体准备”路径 | D准备阶段 |
| 正式接续切换 | 缺少新载体生效、旧卡永久退出、必要归属变更与历史原子保存，以及重复提交/结果未知的核对机制 | D正式接续 |
| 旧凭证永久撤销 | 当前状态检查不等于撤销全部旧短凭证和持续查看资格；需证明恢复状态后旧资格也不会复活 | D授权 |
| 持有人身份、认领、接收人确认 | user/ownership表已有预留结构，但用户认领、所有权确认及转移服务尚未交付；碰卡不证明所有权 | 共用所有权能力 |
| 所有权流转历史 | ownership_history有预留表，无已交付的变更服务和后台查询接口；需区分同持有人换新与真正归属转移 | D所有权 |
| 流转与载体历史查询 | 无管理端按物品查询完整载体/所有权时间线的接口及展示契约 | D历史 |
| 用户侧限定信息及隐私展示 | 当前H5没有限定身份、载体代次、流转摘要返回；须明确公开、本人、管理员各自可见内容 | 用户侧契约 |
| 操作日志页面 | 后端有最小审计写入，没有Make日志页的管理查询接口；不承诺“不可篡改日志” | 管理查询扩展 |
| 顺延建议编号 | 目前由前端提供业务编号，后端校验唯一；Make从本地数组找最大值不保证并发不冲突 | 是否纳入须确认 |
| 图片排序 | 现有资料数组可保留顺序，并非缺少存储服务；Make已有排序交互，是否正式开放需纳入业务范围 | 原型行为确认 |

### 3.3 原稿中不能照搬的实现假设

原Make的换卡函数直接设置新芯片keys_generated、provisioned_at和last_counter；转售并未更新owner_account_id，也没有限定编号或独立实体记录。挂失只改变数组，却提示真实凭证已立即失效。首轮统一流程补了演示字段、前后归属和准备阶段，真正效果仍须由后端实现证明。

原稿用本地数组过滤、分页和顺延编号，部分字段名/状态与现有API不同；图片使用本地/模拟资产。架构整合时保留这些页面组织与外观，通过适配接真实服务，不复制模拟存储、身份与密码到正式工程。

未被App导入的WorkflowGovernancePage仍在附件源码中，不能据这个未展示文件宣称已有独立治理页面。当前主要入口位于芯片、物品详情及日志页。

## 4. 迭代与后续整合顺序

1. cece先预览限定T恤，依次体验挂失、换新、转售、历史和公开档案。反馈入口、字段、步骤及展示是否合适；旧版保留可比较。
2. 下一轮按反馈继续修改原型，并核对普通资料编辑、状态独立操作、筛选、上传、日志等剩余细节；不靠原型里按钮能点就关闭后端缺口。
3. 原型满意后冻结要做的业务范围。现有A能力优先复用；新身份、所有权和接续能力补接口、数据迁移、权限/资格、原子切换、撤销与恢复技术方案，审核相应新增范围后实施。
4. 在当前任务分支整合，不自动删除分支、合并main或部署。普通已有接口按新展示适配，B/C/D按确认范围分步实现，不要求一次建完整交易/支付平台。

## 5. 首轮仍需决定的业务细节

- 挂失申请与接收人的资格依据、管理员如何确认，是否需要用户侧确认。
- 换新/转售的实体是否允许改变尺码、颜色等属性，相关费用及可继承权益清单。
- 实体准备、发货/签收与正式接续的关系；取消、丢件和争议时保留哪个安全状态。
- 公开档案是否展示转售次数、时间粒度及载体换新记录；默认先不公开前任身份与内部理由。

这些不阻止先审核页面和正常路径，但须在相应正式业务实施前定稿；首轮复选框与示例账号不代替决定。
