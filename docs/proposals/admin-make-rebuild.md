## 一、大方向与范围

### 1.1 管理后台定位

服务管理员的三个日常目标：把数字物品资料维护正确；完成芯片与物品、持有人的必要关联变化；看清物品准备、触碰使用与用户持有情况。功能是否保留，就判断它是否直接服务这些目标。

| 本期保留 | 本期移出或不建设 |
|---|---|
| 款式共用资料、发行约定与最终数量 | 选品、竞品、采购、打样、合同和工厂管理 |
| 数字物品、必要的当前/历史实体信息 | 全渠道订单、付款、退款和销售流水 |
| 芯片登记、绑定、配置核验、停用与接续 | 店铺上架/停售、多店商品映射、自动派单和物流跟踪 |
| 当前持有人、必要归属历史与已约定权益摘要 | CRM、营销标签、积分、会员运营和独立客户录入 |
| 核心统计、必要业务历史、操作审计和运行检查 | 单独发售任务中心、首次交付流水线、通用审批/字段/发布平台 |

清理、误绑定纠错仍是已确认的实际需求，保留在相关对象维护中，按第2.6节的资格边界审核；不因精简而取消，也不提前开放未定操作。批量、导出、图片排序/裁剪、回收站和多标签冲突界面不自动纳入本期。

### 1.2 四个关键边界

1. **订单和物流不维护，发行结果必须维护。** 固定50个数字身份仍受50的上限保护。帽子预估100而最终售出137，在外部完成销售核对后，在发行约定确认最终137及核定依据；不录入137条订单。预估量、工厂和收件安排不再是建档前提。核定依据仅保存必要外部引用或简短说明，不新增上传销售明细和客户资料的功能。
2. **压缩履约步骤，保留数字关系变化。** 换新/转售可以只保留准备、确认接续两个操作阶段；当前实体、新旧芯片及必要归属要准确保存。取消订单流水不等于可以直接覆盖旧关联或删除历史。
3. **用户数据限于账户与持有关系。** 使用稳定用户ID，联系方式按权限展示。购买人、收件人、碰卡人不自动成为持有人；不在物品表用手填姓名代替认领。真实短信首次认领已接入，杭州test证据见验收清单，不作为建档配卡的前置。
4. **统计回答准备、使用、持有三个问题。** 看物品/芯片准备状态、有效触碰及趋势、已建立的用户持有关系。销售额、客单价、工厂进度和物流时效交回电商平台。未接入用户服务显示“未接入”，不能用匿名碰卡推算独立用户。

### 1.3 不随收口撤回的原则

- 数字物品ID、发行引用和正式编号在换新/转售后保持；替换实物不增发数字身份。
- 类别只在款式维护；名称、介绍、材质、养护与图片共用并同步引用。发行承诺和每次实体实际规格独立，不被共用保存追改。
- 一件数字物品同一时刻只有一个当前持有人、最多一个有效实体/芯片；挂失时允许暂时没有有效芯片。
- 物品启停、芯片服务状态、发行确认和所有权确认分别表达；保存资料不隐式启用或认领。
- 原安全、真实配置核验、不可任意修改身份、失败保留、未知结果核对、必要审计与图片配套恢复保护继续有效。

## 二、信息架构、功能架构与核心业务流程

### 2.1 建议的信息架构

5个一级入口服务当前任务，不再以“新建发售”作为后台主线。下面为已确认的目标菜单，正式页面只开放已经交付的能力。

| 入口 | 主要内容 | 操作位置 |
|---|---|---|
| 工作台 | 物品/芯片概况、有效触碰、已接入的用户与持有数据 | 统计可带条件进入物品、芯片或必要持有明细；不展示销售/物流待办 |
| 款式与发行 | 款式资料、发行约定两个工作区 | 建款、维护共用内容；保存/确认约定；限时定量确认最终结果 |
| 数字物品 | 稳定数字身份、当前整套物品（实物＋芯片）、持有人与权益、历代物品 | 登记实体、安装、核验、挂失、换新和转售在物品档案中操作；物品详情提供手机页预览 |
| 芯片管理 | 登记、批次、配套首套物品、密钥/配置核验与技术停用/恢复 | 只显示所属整套物品及其挂失事实；挂失/换新/转售回物品详情，无独立芯片挂失动作 |
| 系统管理 | 操作日志、系统与环境 | 默认展示业务审计，另有运行检查和账户与持有查询 |

持有人和历史实体是引用视图，不分别建一套普通录入模块。换新办理中的准备记录可保留并继续，入口挂在物品，不要求恢复工厂、订单、发货等前置阶段。

### 2.2 信息关系与数据职责

| 信息 | 保存什么 | 与其他信息的关系 |
|---|---|---|
| 款式 | 共用商品内容和适用规格 | 一个款式可有多次发行，是类别与共用资料的唯一来源 |
| 发行约定 | 发行方式、数量确定方式、编号规则及确认结果 | 每次关联一个款式；系列暂作归类，不建设多款共用编号池 |
| 数字身份（物品档案） | 稳定身份、发行引用、#001/100、启停、权益和持有历史 | 换新/转售均沿用；不因整套物品被替换而新增发行名额 |
| 实体物品 | 独立实体编号、款式、实际规格、可追溯批次 | 安装前可登记、查找及核对随件编号 |
| 芯片 | 芯片 UID、登记、配置核验及服务状态 | 安装时引用该枚已登记芯片，技术状态可独立核对 |
| 整套物品（装配记录） | 数字身份、实体、芯片、代次、安装确认、挂失、生效与退出事实 | 每代实物与芯片共同准备、共同生效和退出；稳定数字身份可跨代延续 |
| 用户与持有关系 | 稳定账户、当前及历史持有起止 | 从认领/转售业务产生，普通编辑不手工改写归属 |
| 权益与操作记录 | 已约定规则、按物品的年度事实、绑定/接续依据 | 余额和历史从有效业务产生，不再另录一份手工台账 |

cece在2026-11-06明确并授权：挂失、换新、转售的业务对象是整套物品，不是独立芯片。款式保存共用资料，数字身份维持长期身份/权益/统计，每一代整套物品保存具体实物和配套芯片。界面仍为一份物品档案，不为这三层再增菜单。

这些是业务职责，不代表要新增同样数量的数据库表或页面。缺发行的旧资料仍按件兼容；当前分支已构建款式/发行/整套/接续服务，首次用户认领已接入，杭州test短信与实卡已有证据，具体范围见验收清单和CHANGELOG；不能按相同款式文字自动合并旧数据，不能把技术project直接当作可任意改的业务类别。

### 2.3 功能架构

| 功能组 | 核心动作 | 必须得到的结果 |
|---|---|---|
| 资料维护 | 建款、共用编辑、图片维护、资料预览 | 引用物品显示一致；保存提示影响范围；不追改发行和实体历史 |
| 发行维护 | 保存草案、确认约定、核定限时最终量、查引用 | 确认规则和确定最终量分开；已确认承诺不可普通重写 |
| 建档与首次配卡 | 选发行建物品、登记/选择实体和芯片、确认安装、芯片核验、启用 | 不重复身份、不突破固定总量，真实配置通过；不自动认领 |
| 状态和接续 | 临时停用/恢复、挂失、换新、转售 | 按条件切换当前授权；稳定身份和历史保持；转售另变更持有人 |
| 查询和统计 | 基础/高级查询、对象往返、核心指标及明细 | 服务端全量筛选和一致总数；口径、时间及未接入范围可见 |
| 受控维护 | 必要审计、未保存/未知结果保护、合格数据清理及专用纠错 | 保护已有数据、身份、授权和统计；未定动作不伪装可执行 |

### 2.4 核心业务流程

<a id="assembly"></a>

**首次准备：建款 → 确认发行约定 → 创建数字身份 → 核对实体编号和芯片 UID → 确认安装 → 芯片核验 → 启用。**

从「数字物品详情 → 当前实体 → 安装芯片」进入。换新和转售从办理单的「准备新整套物品」进入，复用同一组核对字段，并显示原整套物品和办理单。

1. 只读显示名称、数字物品编号、发行及正式序号。限时发行封版前显示「发行编号待核定」。
2. 必选实体编号，选中后显示款式、实际规格和当前装配状态；找不到时可登记实体，返回时带入新档案。实体编号可与实物或随件标签核对。
3. 必选芯片 UID，显示批次、占用及配置状态。服务端提交时重查实体和芯片的适用性、占用情况及数据来源；每件实体和每枚芯片同时最多参与一套生效组合。
4. 提交前并排核对实体编号、实际规格及芯片 UID，确认实物已安装。系统记录代次、安装确认人和时间。首次装配显示「已安装·待核验 → 核验通过·待启用 → 已启用」。核验失败保留装配记录，支持查看结果和重新核验。
5. 安装确认前可改选；确认后从专用纠错入口处理。已核验或已启用的组合按专用纠错范围办理，具体授权和恢复条件另审。替换组合在核对实际交付后生效。

芯片可以提前登记，不强制按该顺序采购或入库。物品登记选择已确认发行，自动取得款式与类别；系统物品编号和正式序号分开。芯片详情和物品详情调用同一绑定/配置能力，自动带入目标并保留来源，完成后回到同一物品。工厂接单、质检记录、销售订单、发货和签收不再是后台必经页面；启用仍检查资料、发行、关联及真实配置条件。

**发行方式只改规则，不按物品类别建立流程。**

| 方式 | 确认发行前维护 | 结果与编号 |
|---|---|---|
| 固定总量 | 固定正整数总量、对外发行条件和编号规则 | 如50个身份；正式序号在1–50且发行内唯一，售后不释放或新增发行名额 |
| 限时按销量定量 | 销售起止、有效销量核定口径和编号规则 | 期内稳定身份可准备，正式编号/分母待封版；外部核对后确认137等最终量，之后不得普通改总量 |
| 非限定 | 不限量方式与逐件编号规则 | 不设总量，仍逐件编号；不能把“总量待核定”当非限定 |

**限时最终量：打开发行约定 → 填最终数量和核定依据 → 核对已建身份/冲突 → 确认封版。**

不再要求逐店停售、逐店对账或输入订单件次。后台不声称能验证全部外部销量；管理员对核定结果负责，记录确认时间与依据。最终量不得小于已正式纳入本次发行的身份数量，存在多建、待核或归属冲突时先核对，不能自动删身份凑数。未建档名额可以后续准备，不为封版批量虚造实体/芯片。

移除订单之后，原型按付款时间/店铺/订单排序的编号方案同时退出。**已确认编号方式：** 以最终确认的身份范围、稳定建档顺序及唯一标识分配已准备身份的正式序号，余下序号供后续建档；仅新限时模式适用，已固定/封版的编号不重排。超量准备草稿的退出规则须与第2.6节一起定稿，不能把“草稿”直接当正式发行。封版前若实体包装必须印最终编号/总量，该部分仍要等结果确认。

<a id="item-rights"></a>

**数字物品权益。** 换新、转售是新发行数字物品的标准权益，由 BUMBUM 统一定义。物品建档时写入两项适用权益和规则版本。以对外发行确认时间匹配当时有效的标准规则，同批物品分次建档也沿用同一版本。后台只在「数字物品详情 → 持有人与权益」展示适用规则、当前办理资格和办理记录。既有真实物品如有历史承诺，按原承诺处理。旧模拟样本按[批次重建](#sample-reset)处理。

**挂失：物品详情 → 确认当前整套物品及挂失依据 → 记录该代物品挂失，同时停止其配套芯片服务。**

挂失记录属于当时这一代物品，包含代次、规格、配套芯片及已知时间/依据；数字身份、持有人、发行编号和额度不变。挂失立即阻断该整套物品的有效触碰，不增加触碰次数；芯片页不能通过普通技术恢复解除物品挂失。解除挂失政策仍待定，不新增假恢复入口。

**换新/转售：从物品详情核对原整套物品 → 准备替换物品（新实物＋新芯片） → 核对实际交付并生效。**

界面统一为“准备替换物品／确认交付与生效”两阶段，可保存继续。新实物规格先录，配套芯片在新物品内选择/配置；不把换绑芯片当业务主线。确认界面并排展示原、新整套物品及接收账户，准备阶段锁定原物品记录，确认时重查对应。完成后查看办理记录仍显示当时原、新物品，不用新的当前物品替代旧对象。物流在外部办理，不增加运输步骤。

| 场景 | 必须保留的结果与已确认原则 |
|---|---|
| 定期换新 | 持有人不变，整套新物品生效，旧整套退出当前授权，身份/编号保持。准备期间原物品原则上继续服务；此时挂失则保留新物品准备，按挂失换新继续，不另造记录或扣次数 |
| 挂失及挂失换新 | 先标记原整套物品挂失并停止配套芯片服务。换新完成后旧代挂失记录保留，新代正常，不把挂失永久附在数字身份上；准备/关闭/异常均不自动恢复原物品 |
| 后台转售 | 沿用已确认模式：向新持有人交付新整套物品（新实物＋新芯片）；原物品由原持有人保留并退出当前授权，数字身份与权益延续，持有关系在确认交付时变化 |
| 临时停用/恢复 | 停服务并保留关联；恢复检查当前绑定及资格。已替换退役旧卡不能通过普通恢复获得授权 |

定期与挂失换新沿用付费权益，费用另定；共用每个自然年一次额度。以北京时间的**确认交付生效日**计次，例如 12 月准备、1 月确认生效，计入新一年的额度，确认时重查该年可用次数。转售继承物品该年使用记录与剩余额度。旧实物由原持有人保留，尺码可按约定调整，颜色按原发行约定或明确例外处理。

常规转售核对原持有人同意和接收人接受，双方均须有已验证手机号的账户，接收方为另一有效账户。核对依据随办理单保存；有争议或身份与办理对象无法对应时转入实名核验，通过后才可确认生效。交付确认时重查原整套、当前持有人、新实体、新芯片核验、接收账户与交付依据；一次提交完成新整套生效、旧芯片退役、办理单完成及必要的持有人切换或换新计次。重复提交返回同一办理结果。

费用、冻结、取消/争议处置、解除挂失、旧卡展示和已核验装配纠错的具体政策仍需独立确认。单独换芯片的维修属于独立范围。

### 2.5 核心统计与用户数据

售出与认领分别记录。已售出指外部销售已满足发行约定的有效成交条件，并明确对应到这件稳定数字身份，由管理员确认；已认领指已建立有效持有人关系。买后未认领及赠品已认领均可能存在，不能以绑定所有者代替售出。

后台只维护售出确认与首次售出时间；首次确认可登记有依据的实际成交时间（默认当前、不晚于当前），已有首次时间不通过普通维护改写，操作时间与依据另留审计；支持单件或批量确认，不录订单/金额/物流。取消/退款需要更正销售标记时留操作记录，不自动改变身份/归属或删除触碰；换新/转售不重置首次售出时间，也不使同一身份累计售出数增加为多件。

| 实际问题 | 核心指标 | 口径与边界 |
|---|---|---|
| 准备得怎样 | 物品总数、启用/未启用；芯片总数、待绑定/待配置/可用/停用等 | 数字身份与实物/芯片数分别统计，挂失/退役不作空闲库存 |
| 售出后有没有被使用 | 已确认售出物品数、有效触碰次数、被触碰物品数、日趋势 | 默认只计当前已确认售出的身份，事件不早于首次售出时间；近7日/30日/累计及北京时间边界可见 |
| 全生命周期使用 | 跨历史芯片全部有效触碰及逐芯片明细 | 可切换查看，售前真实试碰仅进入生命周期；配置核验不计用户触碰，同一读数刷新不重复计次 |
| 用户建立什么关系 | 已认领物品数、当前持有人数、必要持有明细 | 按稳定账户/有效关系去重，不用匿名触碰算独立或活跃用户；未接入显示未接入 |

按稳定物品ID汇总，#001不是跨发行唯一键。事件保存发生时物品ID、芯片ID、时间及去重读数；不按当前绑定反查历史，不累加硬件计数器。A/B/C分别10/6/4次时，同一物品累计20次、被触碰物品数1；同一时刻最多一枚当前有效卡，退役卡再碰不增加有效次数。转售不把历史访问者改成现持有人。生产验证开关不单独回改历史；直接删除及关联事件清理按第2.6节处理。

### 2.6 清理、纠错和旧资料补齐

cece在2026-11-06明确：芯片和物品都提供生产验证开关，**有标记即可直接删除，无需按绑定、配置、启用、归属、触碰、候选占用或历史状态校验**。本决定替代此前L1/L2清理资格的待审限制；新建和已有记录都可开关，未标记的既有记录默认关闭。

| 范围 | 已确认规则 |
|---|---|
| 生产验证物品/芯片 | 开启开关后显示直接删除按钮，点击即执行，不要求原因、额外业务核验或二次资格确认；未标记对象不提供该入口 |
| 关联处理 | 当前实现按仅删除目标对象处理：清理其触碰、接续及关联，保留另一侧物品/芯片档案，不连带删整条关系链；删除物品时解除对应芯片的关联，已绑定转待绑定，其他状态、密钥标记和计数保留；删除芯片时移除物品内对应实体引用，物品身份/持有人等事实保留 |
| 审计与统计 | 开关和删除留操作审计；开关本身不回改触碰统计，直接删除清理的事件随之退出统计。发行总量和其他物品编号不重排，内部ID不复用 |
| 未标记对象 | 继续走既定启停/挂失/接续等路径，不能通过直接删除命令移除未标记数据 |
| 身份或绑定纠错 | 普通批次/内容可编辑；配置前草稿装配已有受限undoInstall；错UID、错类别/技术项目、错发行/序号及已核验误绑定的专用路径仍待定，不能只改数据库关联 |
| 旧物品补齐发行关联 | 非归档、确实缺失时核对原承诺后补同款确认发行；不改已有正确身份、持有人、实体和年度事实 |

真实服务的清理接口和权限以 [API 实现概览](../../API_CONTRACT.md#04-当前能做到哪一步) 为准。生产验证开关及删除资格已确认。关联范围已由cece明确确认：删除当前对象、另一侧保留；实现、界面说明与检查使用同一口径。

<a id="sample-reset"></a>

**验收模拟数据按批次重建。** 旧样本无需逐件接续。执行前按批次预览数量、来源和外部关联冲突；仅确认范围内的模拟批次可进入清理。复用批次清理与生成机制，覆盖实体待装、已装待核验、启用、售出后零有效触碰、待认领、已认领、跨年换新、转售继承年度额度及预览。样本来源保持可辨识。具体备份、回退和执行安排在技术方案及测试发布范围中核对。

### 2.7 状态分别表达

| 对象/行为 | 应表达的状态 | 不能替代什么 |
|---|---|---|
| 发行约定 | 草案、规则已确认；限时模式另示最终量待核定/已封版 | 不是网店已上架，也不是物品已经启用 |
| 数字身份档案 | 草稿、启用、停用、归档 | 与当前整套物品正常/挂失分开，不用档案启用掩盖挂失 |
| 整套物品 | 待准备、正常、挂失、已替换；历史曾挂失可追溯 | 挂失不只改芯片状态，换新不重建数字身份 |

### 2.8 业务操作审计

默认列表显示时间、操作人、操作、对象和结果摘要，支持按时间、操作人、动作和对象筛选。详情展示前后值、必要依据与关联办理单，可跳转到仍可访问的档案。同一业务事件可出现在全局审计和物品时间线。已删除对象保留历史编号，缺失的旧字段标明缺失。采用参考原型的业务阅读顺序，程序动作与结构化明细用于按权限排查。

## 四、设计规范与交互规范

本轮以**Ant Design Pro官方页面组织和组件使用规范**作为新版目标，Make保留业务参考及合理品牌元素，不再要求复刻其侧栏宽度、固定弹层尺寸或所有排版。旧尺寸属于历史原型基线，不是Pro强制标准；实际容器与截图仍需在新原型审核。

具体规则统一维护在[后台设计与交互规范](../ADMIN_UI_GUIDELINES.md)：ProLayout/PageContainer统一框架，ProTable统一查询/表格，ProForm/ProDescriptions统一编辑/只读，基础控件用AntD；主题Token集中设置。先复用官方模式和配置组合，确有业务缺口再做最小适配，不把安装组件当作界面规范化完成。

新版主页面不出现销售流水线；建档配卡直接进入任务。共用资料可以预览公开内容，编辑预览明确未保存；已保存资料下次成功读取生效，不新增通用发布系统。保存、发行确认、物品启停和正式接续各自表达影响，不能把每个动作串成强制向导。

1280×720及1440×900桌面应能完成核心任务：查询、字段主次、可读详情、底部操作、焦点/键盘、关联返回及失败/未知反馈都需要实际视觉和操作核对。原型只验证范围和体验；真实接口、图片、芯片和所有权分别取证。

## 五、工程路线与审核顺序

推荐**完整官方Ant Design Pro工程迁入Umi Max，承接现有frontend/admin**，不是继续保留Vite应用壳只替换几个组件。用户H5、Python后端、NFC算法和数据库不随框架迁移重写。官方工程可裁剪无关示例和依赖，保留真实路由/布局/启动组织，不整包带入AI、地图、假登录或示例API。

可行性、固定上游依据、版本风险、现有认证/路由/请求与启动链适配，见[工程迁移说明](admin-rebuild-implementation.md)。隔离原型已按官方固定工程重建，采用真实Umi配置路由、运行时、布局及构建；锁文件安装、类型检查和构建已通过。当前分支正式frontend/admin已迁入并接入真实认证及数字档案服务，测试发布与验收范围见TODO及CHANGELOG；预览历史证据不代替正式回归。具体版本、来源与构建适配见工程说明。

已通过的审核顺序：定位和删减范围 → 菜单/核心流程 → 字段和统计 → 设计交互与工程边界。产品与必要技术范围现已通过，当前可预览界面采用官方Umi/Pro工程及同套页面；尚无服务的业务用隔离样例并明确标记，后续复用页面接真实能力，不先重画一套Make再重复迁移。交互预览与正式能力分别验收；合并main、生产部署、数据库或真实卡操作仍分别取得对应授权。
