# 最新 Make 基准的后台重构：原型修改与后端缺口

本稿承接cece于2026-11-04本轮上传的《设计项目管理后台.zip》。先修改Make交互原型，由cece在Figma预览并迭代到满意，再整理涉及新增业务的技术方案，在现有任务分支整合。现有后端与分支保留，不删除、不先推倒重写。当前先整理业务定义、信息/功能架构和设计交互规范，与cece对齐具体改法后再改原型；本轮已获准细化字段展示并更新独立审核图及说明；不覆盖原始Make，不修改正式应用、接口、表结构或部署。

## 1. 已确认目标与本轮边界

- 页面框架、前端组件、视觉风格和交互体验尽可能沿用这份最新Make。需要修改的业务含义直接在原稿调整，不另做一套后台样式。附件中的规则文件只是外部参考，不替代仓库协作规范。
- 挂失、换新、转售要能接续新芯片；限定物品的数字身份与专属编号保留，例如限定T恤的`#001/100`在换新和转售后仍为同一号。替换实体不增加数字发行数量。
- 同持有人换新不改变所有权；转售必须换新实体及芯片并记录前后持有人。身份、实体、芯片、所有权分别记录，不能只覆盖芯片关联或复制旧芯片全部数据。
- 用户侧对外展示与内部记录分开。前任账号、联系方式、私人内容、申请证明及内部处理原因不自动转移或公开。
- cece已取消React 19独立组件冒烟的固定要求。后续按实际改动选择类型/构建和必要业务验证，不重复跑独立组件矩阵；如确有需要，先说明理由、范围和预计耗时，获cece明确批准后再执行。图片配套备份恢复的生产必要门槛保留。

物品归档、批量功能、真实支付/交易平台，以及B清理/C纠错的具体策略，不因Make中出现可点按钮就视为全部获批。具体资格证明、费用、可继承权益及履约异常仍待确认；已同意的交付核验后正式接续方向及自然年换新规则统一见[D接续提案](replacement-resale.md)。设计及通用交互只在[后台设计与交互规范](../ADMIN_UI_GUIDELINES.md)维护。

## 2. 原稿基准、信息架构及场景流程

### 2.1 信息架构与功能职责

六个业务对象已确认：数字物品身份、实体载体、芯片、持有人、操作记录、数字权益。概念边界见[产品愿景](../../PRODUCT.md#3-统一概念账户数字藏品实体载体和芯片)，权益详细规则见D提案。对象不必各建一个一级菜单，避免把数据模型直接照搬为导航。

| 工作区 | 管理员关心的信息与功能 | 当前边界 |
|---|---|---|
| 登录与会话 | 账号/密码/TOTP、会话恢复、失败反馈、运行状态、退出 | 复用真实认证；账号创建/重置仍走受控管理流程 |
| 工作台 | 库存、待处理提示、真实触碰统计和快捷定位 | 复用已交付查询，不伪造待办数量 |
| 芯片管理 | 登记、批次、状态、首次来源、绑定物品引用、配卡与核验 | 身份/硬件操作归芯片；关联链接进入物品详情；停用/挂失/退役和专用纠错仍有后端缺口 |
| 物品管理 | 稳定身份/发行编号、资料、当前实体与芯片、持有人、数字权益、历史 | 现行普通维护复用；独立实体/所有权/权益模型尚未交付，不在详情顶部堆完整履约流程 |
| 款式/发行资料 | 共用尺码表、允许尺码、颜色与发行约定 | 先明确资料维护职责，具体入口后续对齐，不立即增加一级菜单 |
| 业务处理 | 挂失保护、换新申请与准备/交付/接续、后台转售 | 从对应信息分区进入同一处理流程，复杂流程建议独立处理界面；布局须先审核 |
| 维护、清理与纠错 | 废弃数据资格/引用检查、专用纠错、处理结果与操作历史 | B/C独立审核，不靠普通编辑或本地删除按钮替代 |
| 操作历史/系统状态 | 查询操作人、对象、动作与结果，定位故障 | 当前仅部分审计写入及运行检查；完整日志查询接口未交付 |

用户侧只提供约定的数字内容/权益及流转信息查看，本期不开放发起转售入口；前任身份与私人资料按权限隔离。原稿未被App导入的页面不能作为现有导航或已交付能力。

### 2.2 按实际场景梳理流程

下表覆盖当前后台重构相关场景；不替代A/B/C/D对输入、资格及异常的逐项定义。正常维护已有能力和提议能力必须分别接入，不能用原型可点击代替业务交付。

| 场景 | 管理员操作路径及关键结果 | 需保留的边界 |
|---|---|---|
| 登录/恢复/退出 | 打开后台 → 核对账号、密码、当前TOTP → 登录 → 到期或退出后回到登录 | 错误反馈、真实会话/CSRF和安全退出；不复制假登录及预填凭据 |
| 芯片登记/连续登记 | 扫描或输入UID → 重复核对 → 选择项目/批次 → 保存 → 查看确切新记录或继续登记 | UID冲突不重复造卡，失败保留输入；首次来源与批次如实记录 |
| 创建物品/连续创建 | 选择项目、业务编号和款式 → 录入资料 → 图片暂存 → 保存关联 → 查看或继续 | 未知结果先核对确切对象，取消不改变已保存图片；不复制本地顺延号逻辑 |
| 首次绑定与配卡 | 从芯片核对物品引用 → 首次绑定 → 受控密钥/写卡 → 配置核验 → 查看结果 | 真实卡核验不以勾选代替；当前唯一关联约束保留 |
| 查询与关联查看 | 筛选查询 → 打开详情 → 点关联芯片/物品 → 返回原查询上下文 | 已生效条件、分页及来源恢复；不只依赖页面保活 |
| 查看/编辑资料 | 详情核对 → 修改允许字段/图片 → 校验并保存 → 返回同对象 | 同字段只读/编辑；状态独立操作；失败、关闭和离开保护 |
| 临时停用/恢复 | 从芯片状态分区核对影响 → 确认动作 → 查看真实结果/历史 | 不等于挂失/退役；操作API及恢复资格未交付 |
| 废弃芯片删除 | 查到目标 → 核对是否确属可清理数据及引用/配置/关联 → 展示影响 → 按B规则确认 → 核对结果 | 未定义资格前不开放删除；生产/已配置/有历史对象不因“废弃”直接物理删除；符合条件的专属验证数据按B定稿处理 |
| 废弃物品处理 | 核对关联芯片、媒体、历史及清理资格 → 区分清理与退出 → 确认处理 | 不借删除抹掉真实流转/审计；编号复用与统计政策由B定义 |
| 录错纠正 | 核对项目/编号/绑定事实 → 区分未配置与已配置 → 专用C流程 → 核对前后结果 | 不用普通PATCH改稳定身份，不绕过已配置卡的保护 |
| 挂失/解除 | 核对申请人及当前实体 → 明确阻断范围 → 确认挂失；找回后另核对解除条件 | 不自动扣换新次数；已退役不可普通恢复 |
| 定期/挂失换新 | 核对持有人及额度 → 目标尺码/颜色规则 → 准备候选新实体/卡并核验 → 交付 → 管理员核验后正式接续 | 同持有人、编号不变、共享年度额度、旧实体不回收；跨年办理及扣减时点待定 |
| 后台转售 | 核对前后持有人及权益 → 明确冻结 → 准备新实体/卡 → 交付核验 → 正式变更归属和授权 → 查看历史 | 旧实体保留；不扣或重置换新额度；用户仅查看流转摘要 |
| 处理失败/取消/争议 | 按准备/运输/接续阶段核对实际结果 → 决定继续、取消或专门处置 → 保留记录 | 不盲重试正式切换，不自动复活旧卡；异常政策须定稿 |

### 2.3 先对齐再修改

展示基准始终是cece原始最新版压缩包，具体尺寸、分区、控件及状态见统一规范。cece已整体认可现有页面改动方向、挂失/换新/转售及发行资料审核图，并授权细化字段展示和实体术语；按本节及第2.4节更新独立审核图。后续如改变已同意的主入口、主要容器或业务步骤，仍先对齐受影响部分，不为普通字段排版重走整套审批。

### 2.4 已同意的三层信息与字段展示

cece已认可页面整体方向，并同意细化字段、界面用“实体”替代“载体”，明确区分以下三层。这里定义展示归属，不代表现有数据库已完成分层，也不新增普通编辑权限。

| 信息层 | 管理什么 | 页面与维护位置 |
|---|---|---|
| 共用款式／发行资料 | 款式编号、尺码表与可选尺码、发行颜色及例外约定、发行系列／总量、约定的权益规则 | 商品资料中的款式引用打开共用资料；已发行条款只读，不在换新办理中改约定；具体新增/修订权限待定 |
| 每件数字物品身份 | 唯一物品编号、项目、限定序号、当前持有人及归属历史、权益使用情况；关联本件展示资料 | 物品详情为核对入口；编号与归属不能通过普通编辑修改，权益通过专用办理更新 |
| 每次交付的真实实体信息 | 实体记录、交付次序、实际尺码/颜色、关联芯片、准备/交付/接续/退出记录 | “当前实体与历史实体”分区；目标尺码在换新申请选择，新交付写新记录，旧记录保留 |

**现有资料兼容：** 当前名称、介绍、材质、养护及图片按每件物品保存，本次不自动迁为同款共享，不因更新某件物品而修改其他物品。共用资料未来的默认值、覆盖与迁移政策需在技术方案明确；当前款式编号只是可空/可重复的文字，不能把它当已有的款式库关联。

| 物品详情分区 | 具体字段及操作 | 普通资料编辑态 |
|---|---|---|
| 基本信息 | 物品编号、项目、资料状态、创建/更新时间；计划增加发行系列、限定编号、当前持有人、首次绑定所有人时间 | 同字段只读展示；“首次绑定所有人”不同于首次绑定芯片。资料状态不等于芯片或权益状态 |
| 日常维护 | 编辑资料入口、按条件提供的独立启用/停用；不另建一套款式/状态/验证标识表单 | 不重复呈现另一组保存按钮；启停不混入资料保存，验证标识仍按B提案定稿 |
| 商品资料 | 款式编号、名称、介绍、材质、养护说明、图片、尺码表；共用资料引用 | 服装放开款式、名称、介绍、材质、养护、图片；尺码表只读。饰品当前仅款式可改，已有名称/介绍/材质/寓意/图片只读 |
| 当前实体与历史实体 | 当前实体记录与交付次序、实际尺码/颜色、芯片引用/状态、密钥生成与配置核验摘要、正式接续时间；历次实体的对应事实与退出原因 | 全部只读；挂失靠近当前芯片，换新从数字权益进入。不得在普通保存中覆盖旧实体历史 |
| 数字权益与办理记录 | 换新年度、剩余次数、约定规则、进行中/历史办理记录、转售说明 | 同字段只读；申请换新/后台转售进入独立流程，不将按钮状态当已交付接口 |
| 所有权流转记录 | 当前及历任持有人、起止/变更时间和办理引用 | 全部只读；同持有人换新不伪造一次所有权转移，用户摘要按隐私规则另展示 |

详情与编辑保留相同适用字段。编辑中只读关联和历史可用描述列表/可展开分组，不能省略数字身份或把历史当可编辑表单；用户视角预览仅展示允许公开的商品资料，不展示后台持有人、资格证据或内部历史。

### 2.5 当前录入字段与未来字段的区别

以下按当前分支表单和服务端校验核对，具体限制以[芯片规范](../product/chip-lifecycle.md#1-芯片登记与首次来源)、[物品创建与编辑规范](../product/admin-management.md#2-物品草稿创建与列表)及[接口](../../API_CONTRACT.md#4-管理物品)为准，不能因审核图展示了字段就推定当前可录入。

| 当前录入入口 | 手工字段 | 必填与可修改边界 |
|---|---|---|
| 芯片登记 | UID、项目、批次 | UID必填且不可普通修改；项目可暂不分配，未分配时首次绑定按物品确定；批次选填，可补录/修改/清空。首次来源、状态、关联、密钥及时间由系统/专用流程产生 |
| 物品草稿创建 | 项目、物品编号、款式编号 | 项目与唯一编号必填；款式选填且可重复。项目/编号无普通修改入口，款式可修改/清空；创建仅产生草稿，不绑定所有人或自动启用 |
| 服装资料补充/编辑 | 名称、介绍、材质、养护说明、图片；款式可同次保存 | 保存资料时名称必填，其余选填；尺码表当前只读。仅改款式不强制先创建名称；归档不可编辑，启停独立 |
| 饰品普通编辑 | 款式编号 | 其余已有资料只读，尚未交付完整饰品资料录入入口 |

发行系列/限定编号、独立实体的实际尺码/颜色/历史、持有人及年度权益均是计划新增能力。审核图使用符合当前物品编号格式的合成编号，限定编号另列；不能以演示编号替代现有FASH/JEW格式约束。图片上传能力是否启用仍由真实服务配置与生产恢复门槛决定，不因原型显示Upload而启用。

### 2.6 已认可的现有页面保留与调整清单

本表补齐已向cece交付并获整体认可的逐页范围；物品字段细化以第2.4节为准。去掉的是明确列出的原稿行为，不因缺少后端而取消已确认需求；B/C资格及D待定业务政策不因布局认可而自动获批。

| 页面／区域 | 保留 | 去掉或替换 | 调整与新增 |
|---|---|---|---|
| 应用框架与顶栏 | 侧栏、顶栏、白底卡片、蓝色主色、字号与间距；管理员身份及退出位置。 | 日常界面里的模拟接口失败开关；没有明确用途的占位入口。 | 故障演示放独立审核说明；保持内容区独立滚动、返回上下文与矮窗口可操作。 |
| 登录页 | 账号、密码、Authenticator验证码、登录按钮、运行环境检查与帮助说明。 | 预填演示凭据、绕过认证与固定成功反馈。 | 补登录中、失败、会话过期和恢复；退出后清除会话，未保存内容先处理，不默认另加一次退出确认。 |
| 工作台总览 | 库存卡片、统计范围、有效触碰趋势与库存快捷查询。 | 把本地数组数字当真实统计；跳到未交付业务的假快捷入口。 | 保留项目/时间/关键词口径；已生效条件可见；无数据、加载、失败分别展示。 |
| 芯片列表与登记 | UID、项目、批次、来源、状态、关联物品、日期；查询重置/高级条件、登记并继续。 | 仅靠本地数组判断UID不重复；模拟手机批量登记假装真实完成。 | 关联物品可点；登记后定位确切记录；手机批量路径如已支持则复用真实回执，不取消需求。 |
| 芯片详情 | 基本信息、日常维护、关联与配卡、状态管理分区；批次维护和真实密钥保护。 | 将挂失、停用、退役混为一种状态；原稿直接完成接续的“更换新芯片”动作。 | 挂失留在状态区；换新跳至物品权益办理；退役展示历史；恢复、解绑和清理按资格分别处理。 |
| 首次绑定与配卡 | 独立绑定弹窗、目标物品核对、受控密钥生成/查看、配置核验区。 | 勾选后自动视为写卡完成；用首次绑定覆盖历史关联或接续旧身份。 | 阶段结果分别呈现；候选新卡准备在换新办理中引用专用流程，不能绕过核验。 |

## 2A. 历史首轮演示记录（不作为下一轮设计基准）

此前AI提前修改的首轮原型并未获得页面改法确认，其在物品详情顶部放置生命周期操作区的做法已被cece否定。以下保留为历史说明和交付限制，不作为已批准入口/步骤；下一轮从原始Make及第2节重新对齐，不继续沿用该改稿。

### 2A.1 操作入口

历史首轮曾建议以**数字物品详情**作为挂失、换新、转售的主入口。它承载稳定身份、限定编号、当前持有人和历次实体；管理员从这里能看到一次业务会影响什么。

芯片页保留登记、批次、配卡核验、硬件状态及关联查询。芯片页发现损坏/丢失时，跳到对应物品处理同一流程，避免芯片、物品两个页面各维护一套换新逻辑。未配置的误绑定仍归专用纠错，不能混成所有权转移。

首轮保留最新Make的侧栏、顶栏、列表、详情抽屉与表单样式，新增“物品身份、载体与流转”区；重复的可见挂失/接续入口统一到该区。其它原稿页面尚未逐项重做。

### 2A.2 限定身份、实体与所有权

| 对象 | 限定T恤示例 | 换新 | 转售 |
|---|---|---|---|
| 稳定数字身份 | 数字物品编号＋发行系列＋`#001/100` | 保留 | 保留 |
| 实体载体 | 第一件T恤及其实体编号 | 新增第二件，保留第一件历史 | 新增交付给接收人的实体，保留旧实体历史 |
| 当前芯片 | 当前实体上的认证入口 | 接续新芯片，旧卡退役 | 接续新芯片，旧卡退役 |
| 当前持有人 | 示例持有人甲 | 保持甲 | 变为示例持有人乙，记录甲→乙 |
| 历史与隐私 | 载体轨迹、归属变化、内部证据 | 保留必要历史 | 保留必要历史，前任私人信息不随物品公开 |

限定编号须在对应发行系列内解释，不能取代系统唯一物品编号；普通非限定物品不强行补`#001/100`。当前已确认尺码可调整、颜色按发行约定限制；旧演示未完整表达，具体规则统一见D提案。

### 2A.3 演示步骤

- **挂失：** 核对申请与当前物品 → 确认冻结范围；保留数字身份、限定编号和持有人，当前载体挂失。挂失本身不立即换卡或删除历史。
- **换新：** 核对申请/现持有人 → 准备新实体及新芯片 → 对照前后信息确认接续；持有人不变，实体代次增加，旧卡退役。
- **转售：** 核对原持有人与另一位接收人 → 准备新实体及新芯片 → 确认接续与所有权变更；记录前后账号，身份/限定编号保持不变。
- **用户侧预览：** 以公开档案视角查看作品、限定编号、服务状态与流转摘要；不显示管理员可见的账号、手机号、内部原因。

新增限定T恤和三位持有人均为合成样例。步骤中的资格和准备确认只演示界面，不是正式核验方式；真实版本不能用复选框代替持有人资格证明或实卡核验，也不能点击“下一步”就自动生成密钥、视为写卡完成。公开流转次数/摘要属于首轮展示提案，尚不是最终披露政策。

首轮Figma副本：[BUMBUM后台 · Make改稿01](https://www.figma.com/make/UooGXZe3IW8vHOZGcSUYJ6)。**当前仅创建了空白副本，源码上传被云端代理CONNECT 403拒绝，尚未导入，不能作为可运行预览。** 修改包及本地截图随本轮交付；上传失败后未继续导入或盲重试。环境状态显示网络不限域名，具体代理拒绝原因未确认，不能归因于Make模型额度。导入、预览和人工结论分别记录。当前连接支持向新空白Make导入项目，不支持反复覆盖已填充文件；后续每轮提供独立副本并保留上一版。

### 3.3 原稿中不能照搬的实现假设

原Make的换卡函数直接设置新芯片keys_generated、provisioned_at和last_counter；转售并未更新owner_account_id，也没有限定编号或独立实体记录。挂失只改变数组，却提示真实凭证已立即失效。首轮统一流程补了演示字段、前后归属和准备阶段，真正效果仍须由后端实现证明。

原稿用本地数组过滤、分页和顺延编号，部分字段名/状态与现有API不同；图片使用本地/模拟资产。架构整合时保留这些页面组织与外观，通过适配接真实服务，不复制模拟存储、身份与密码到正式工程。

未被App导入的WorkflowGovernancePage仍在附件源码中，不能据这个未展示文件宣称已有独立治理页面。当前主要入口位于芯片、物品详情及日志页。

## 4. 迭代与后续整合顺序

1. 当前先完成六对象、场景流程和统一设计交互规范，并核对D提案已确认与待决规则；只修改文档，不再直接修改原型。
