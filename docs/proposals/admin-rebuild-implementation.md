# 管理后台重构方案：Umi官方工程迁移说明

本稿承接[主方案](admin-make-rebuild.md)，统一原A技术、Make整合、Pro路线和新增业务缺口。**推荐采用完整Ant Design Pro官方工程的Umi Max组织，落在现有frontend/admin。** 此前“保留Vite只接ProComponents”的推荐进入历史。按cece批准，本轮先在prototypes/admin-make重建完整官方Umi/Pro交互原型；正式frontend/admin仍保持现有可用工程，后续复用同套页面接真实服务。

整体路线已由cece审核通过并授权先重建隔离原型；已批准的认证、图片存储/恢复、芯片算法及原业务保护保持，不因换框架改写。详细契约继续由API、TECH_SPEC及其技术附录维护，本稿不另复制一套接口和密钥规则。

2026-11-06，cece认可当前原型并明确授权在同一分支构建正式代码供测试环境验证。以下原型隔离说明保留其适用边界；本轮正式迁移按第8节执行，不导入原型样例、演示认领或故障开关。

## 1. 可行性与收益、成本

Umi Max（`@umijs/max`）提供应用框架、路由、布局、初始状态和必要插件约定；Ant Design Pro提供后台工程与页面模式；ProComponents提供高级表格/表单/详情等组合；AntD提供基础控件。完整迁入以真实使用这些工程组织为依据，而不只看是否安装了某个组件包。

| 事项 | 对当前项目的判断 |
|---|---|
| 是否值得做 | cece明确要求统一官方工程以改善规范性、减少自定义拼接。新版范围同时收口，适合在正式整合前统一应用壳、页面和导航约定 |
| 直接收益 | 后续页面沿官方目录/路由/布局/表单模式扩展，减少现有手写壳与官方示例之间的适配差异 |
| 不能自动取得的结果 | 框架不会自动解决字段冗余、信息主次、宽度、密度与审美；仍须落实设计规范、实际截图和完整任务验收 |
| 主要一次性成本 | 迁移路由/离开保护、真实登录和请求语义、环境配置、启动与测试脚本，移除重复壳和旧样式；迁移不是原样复制官方示例 |
| 持续成本 | 维护Umi配置和官方版本升级，保持本项目的最小定制与单一请求/会话入口；不额外建设内部组件库或后台框架 |
| 后端与运行资源 | 管理端仍以静态资源交付，保留Python/Flask/MySQL、NFC算法和H5；无需因此增加Node常驻业务服务 |
| 结论边界 | 隔离原型严格安装、Umi类型及生产构建已通过；没有双路线性能对照，不报告未经测量的工时、速度/包体收益 |

**版本冲突须显式处理：** 原A技术曾约定不引入ProComponents 3预发布版；当前官方模板声明的3.1.14-2带预发布标记。这一冲突不能因“完整工程”而自动解除。本轮将官方工程作为目标，本轮核对稳定2.8.10仍声明AntD 4/5，而官方候选3.1.14-2声明AntD 6。隔离原型固定使用官方候选3.1.14-2，已在执行期间说明影响；不降级正式AntD、不强制忽略peer依赖。正式工程最终依赖组合仍须在真实整合前核定。不得用强制安装、忽略peer依赖或退回旧AntD主版本掩盖冲突。

正式实施时固定官方来源、记录必要许可和定制，按严格解析生成npm锁文件；保留项目已定Node构建环境，若实际需要变化先说明。官方模板里不相关的AI、地图、示例数据、外部分析、录制、Mock和发布脚本可以裁剪，不因此改造成继续运行Vite的另一套应用壳。

### 2.1 本轮隔离原型实际采用

保留官方config/config.ts、defaultSettings.ts、routes.ts及src/app.tsx运行时组织，使用max setup/dev/build、官方布局、PageContainer、ProTable、ProForm和ProDescriptions；移除原Vite入口和手写应用壳。上游MIT许可随源码保留，裁剪示例API、分析/录制、AI/地图与无关发布能力；不是复制全部演示功能。

锁定Umi Max 4.7.27、ProComponents 3.1.14-2、AntD 6.6.8、React/DOM 19.3.1、TypeScript 7.0.2，使用项目现有Node 24.19.0/npm 11.9.0。严格npm解析成功，没有force/legacy-peer-deps。采用Umi默认Webpack；开发publicPath为/，生产为./，hash路由支持独立静态预览；按构建器检查启用esbuildMinifyIIFE，避免拆包压缩辅助函数冲突。

演示数据集中在本原型domain/store，不被正式工程引用。v6会话单独保存；若存在旧v5，仅复制核心档案，原记录不改、不由持有关系推断售出，不用旧硬件读数补造触碰。旧履约步骤留在旧会话；复制的旧接续只读，不能冒充新版交付核验。正式认证、首次认领和配卡仍未接入，演示按钮明确标注。启动与导出命令只维护在[本地运行说明](../LOCAL_DEVELOPMENT.md#14-隔离umi管理原型)。

## 3. 迁入哪里、保留什么

| 位置 | 迁移内容 | 必须保留/检查 |
|---|---|---|
| `frontend/admin/package.json`、锁文件、配置 | Umi Max启动/构建和Pro必要依赖；最终替换原Vite管理端构建组织 | 单一React/AntD组合、npm锁、必要命令；不同时长期维护两个正式后台 |
| `frontend/admin/src/main.tsx`、`AdminLayout.tsx` | 承接到官方运行时、布局、路由和PageContainer | 按主方案菜单；现有主入口及手写壳被替代后退出，不能只包一层Pro保留两套 |
| `LoginPanel.tsx`、`api.ts` | 将既有真实认证/请求接入官方运行时 | 密码/TOTP、会话恢复/到期、服务端退出、Cookie与内存CSRF；不接示例currentUser或假登录 |
| `NavigationGuard.tsx`、`adminNavigation.ts`及页面路由 | 适配Umi路由、菜单导航、查询参数和离开保护 | 已提交筛选/页码、返回来源、刷新/直接访问及安全站内跳转；敏感数据和草稿不入URL/持久存储 |
| `ChipPanel`、`ItemPanel`、详情和创建页面 | 按ProTable/ProForm/ProDescriptions及新页面组织迁移 | 服务端全量查询、排序/总数、确切ID、连续创建、只读边界、关联往返；不导入原型本地数组 |
| `ItemImages.tsx`及共用资料 | 复用真实Upload/Image和既有上传/读取服务 | 暂存与保存、取消/失败/未知结果、原图兼容及权限；共用模型/图片归属迁移另审 |
| `TapStatisticsPanel`、`TapDailyChart`、运行检查 | 接入统一框架和必要核心指标 | 保留现有有效事件聚合与真实诊断，不借重构重写算法或伪造用户统计 |
| `make.css`、`MakeSurfaces`、Tailwind与旧样式 | 只保留仍有实际依赖的必要部分，交付流程退出已替代内容 | 先查跨页依赖再删除；优先Token/官方组合，不长期维护两套同类样式 |

API业务页可保留现有类型、调用函数及错误含义，再适配官方运行时。需要使用Umi request时统一接入同一服务入口，不并存两套会话/错误处理。保留`{status,data}`、服务端错误码、Cookie、内存CSRF、超时与结果未知语义，不要求后端改成官方演示响应格式。请求中间件不得自动重试危险写请求，不把真实会话、验证码或密钥接入录制功能。

`frontend/user`继续独立Vite工程、自然页面滚动，不迁入Pro或继承后台布局；`core/`、既有Python依赖、数据库和NFC安全方案不因前端迁移改变。

## 5. 已有真实能力与新增业务的交付边界

| 能力 | 当前依据 | 后续处理 |
|---|---|---|
| 管理认证、登记/查询、首次绑定、密钥/配置、物品资料/启停、图片、触碰统计 | 现有代码及[API概览](../../API_CONTRACT.md#04-当前能做到哪一步)，不是本轮重新运行证据 | 优先保留并迁入新框架；完整任务回归后退出旧页面 |
| 共用款式/发行、独立实体、正式编号与限时核定 | 原型演示，尚非正式业务服务 | 产品确认后补接口/事务/模型及历史冲突归并；不从同码或编号前缀猜测关联 |
| 整套物品准备/挂失/换新/转售 | 业务对象已确认；原型记录每代实物与芯片、代次、挂失事实及办理原新记录ID | 正式服务需为整套挂失同步停卡、整套交付与归属切换提供事务及接口；不能仅调芯片状态或覆盖chip.item_id实现业务 |
| 首次认领、账户/归属、年度事实和用户统计 | 已有预留表/契约，服务未完整交付 | 不把手机号、物流或碰卡当授权；未接入明确显示；转售归属及新旧授权/历史须一致提交 |
| 生产验证清理与C纠错 | cece已确认标记后直接删除，原L1/L2资格限制被替代；C纠错仍待定 | 原型提供开关与直接删除，清理目标关联且保留另一侧和审计；正式接口/事务后续整合，不执行真实数据删除 |

隔离原型在既有实体记录上补代次、挂失时间/依据，办理记录锁定原物品ID及准备新物品ID；同一数字身份内追加整套物品，不创建新发行身份。旧v6会话兼容已有芯片挂失事实和原新对应；不补造缺失时间/审计。验证清理同时清理指向被删除原物品的办理并释放新物品准备，避免失效引用。

接续技术须覆盖已有短凭证和持续查看资格：旧资格永久撤销、当前/历史关联、准备核验不授权益、并发/重试/响应丢失下的一致性。状态恢复不应复活已经失效的旧授权；数据库事务不声称可以回退真实卡片。密钥、验证及锁顺序继续按[TECH_SPEC](../../TECH_SPEC.md)、[实现附录](../IMPLEMENTATION_DETAILS.md)和已批准接口执行，不重写算法、不引入新队列/缓存/订阅服务。

普通保存与必要审计一起成功或失败；正式接续的新旧授权、实体、必要归属与历史一致生效。用户API只返回获准公开字段，前任账号、私人内容、资格证明和内部原因不能迁给新持有人或公开。

## 6. 保留图片配套备份恢复门槛

图片继续现有受控存储/读取和生命周期；精确格式/体积/像素/张数及访问资格只在[API图片契约](../../API_CONTRACT.md#41-私有图片上传暂存与读取)与[实现附录](../IMPLEMENTATION_DETAILS.md#9-服装资料与启停实现)维护。框架迁移不新增OSS、CDN或媒体平台。

原A已批准的必要门槛保留：配套恢复必须核对同一冻结窗口的资料引用、媒体元数据及文件，源上传服务停止、目标上传关闭时仍能独立恢复；缺图/篡改/错对象/错时间点应拒绝。沿用[备份模块](../../core/media_backup.py)、[独立工具](../../scripts/media_backup.py)、[现有恢复测试](../../tests/test_media_backup.py)和[本地手册](../LOCAL_DEVELOPMENT.md#13-a方案生效门槛组件冒烟与图片离线恢复)。既有证据不冒称本轮新跑；共用款式迁移改变归属/引用时另查影响，生产备份前提未具备不启用新上传。

回退保留新图读取、元数据和文件，不删库/图、不覆盖后来记录；服务器恢复和生产资源仍按对应授权执行。图片门槛不替代实卡、量产或杭州整库PITR验收。

## 7. 实施与验证顺序

1. 主方案、字段、设计与Umi完整工程路线已通过；原型已获认可，本轮已明确授权在当前分支构建正式代码；未定业务政策仍不自动批准。
2. 当前预览直接基于官方Umi/Pro工程制作，核对精简任务和实际视觉；未交付服务只用有标记的隔离样例。复用同套页面继续接真实接口，不另造一套长期原型，不先重画旧Make再搬一次。旧长流程53项只属历史，不作为新版或Umi通过。
3. 官方工程在既有admin路径按可回退提交迁入，优先接真实登录、查询和一条建档配卡任务，再覆盖剩余页面；预览中的样例入口与正式服务隔离，正式交付移除假数据/假成功。分步交付便于发现问题，不长期保留两套后台。
4. 新款式/发行/接续等业务按获批技术方案补后端与必要迁移；未交付能力不通过演示状态冒充成功，不以全部后续政策未定为由重写既有基础功能。
5. 完成受影响的类型/构建、业务/API/数据库检查及浏览器实际操作/截图，覆盖两种桌面窗口、查询返回、会话、图片、失败和未知结果。真实芯片/生产验证另取授权和证据；不恢复已取消的React19独立组件矩阵，不把模板自带测试全套变成固定门槛。

验收按主方案四组任务，技术细节由AI核对并说明。人工验收、提交推送、main合并和生产部署分别报告，不因迁入官方工程而自动发布。

## 8. 正式构建的实际技术范围

正式管理端在frontend/admin迁入Umi Max 4.7.27和已验收Pro组件组合，默认Webpack；用户端Vite、Python/Flask及MySQL不更换。真实Cookie、内存CSRF、TOTP、密钥派生与双链接验签继续复用。官方依赖的额外strict-peer-deps解析发现Dva/Utoo等上游peer冲突；默认npm ci会警告，未使用force/legacy-peer-deps，实际启用的Webpack、布局、表格与表单必须经构建/任务回归验证，不能写成全部传递插件严格兼容。

数据库006新增款式、发行、数字身份扩展、历代整套、办理、验证标记及写回执。旧稳定item/chip/ownership/scan_log继续使用；不从名称或SKU猜款式、不猜发行和售出。已有绑定只补第一代及真实芯片挂失事实，未知规格/时间显式留待核对。生成列保持当前整套和待办理唯一；MySQL不允许的生成列基列级联外键改由事务显式清理，外键保留最后防线。芯片新增retired，旧卡不再被普通恢复。

芯片配置允许锁定已保存办理的候选芯片并确定项目，仍须真实两条读数/人工K0确认；候选配置不建立item_id或授予用户资格。整套交付原子结束旧代、退役旧卡、建立新代、切换必要归属并撤销旧tap_grant，保留计数/事件；换新计次仍待核，不增加未知费用或解除挂失入口。稳定身份、发行编号和首次售出不变。

所有新管理写操作使用随机request_id及payload摘要在MySQL保存提交回执；同一管理员同一请求重试返回原结果，不重复审计/增发。结果未知先查回执，未查到仍只允许明确重试同一输入/编号；不自动重发写请求。列表用服务端筛选/总数/10条分页，不把原型数组接入正式工程。新统计从真实pass事件汇总，售出口径另检查显式sold及first_sold_at，账户仅展示真实账户与持有关系。

共用款图沿用既有静态图片解码、缩小和重编码规则；首个正式版将小规模共用款图保存在MySQL style_image中，避免为独立款式引入虚假物品或新的存储服务。每次保存最多20张、上传单张8MiB，受容量限制；图片不以内嵌dataURL或公开文件暴露，管理会话或物品查看资格验证后读取。旧单件私有图片仍用现有受控文件目录与恢复流程。共用图随完整数据库转储保存，媒体配套快照增加内容摘要和共用引用核对；未保存图片24小时到期，后续上传仅清理本款已到期暂存。规模增长时再评估统一存储，不现在扩建媒体平台。

已有库必须先做完整备份再执行006，工具默认只检查，ready拒绝缺失/部分结构。DDL不承诺事务回滚；停止写入、保留备份和现场，未知部分结构不自动删表重建。升级命令在[本地运行](../LOCAL_DEVELOPMENT.md)和[杭州手册](../HANGZHOU_DEPLOYMENT.md)维护。代码回退不删新增表/图/后写数据；旧程序不理解retired和新关系，006后不直接将旧程序覆盖上线。main合并、实卡和环境部署仍需对应授权。

售后验收没有真实持有关系时，仅在明确测试目标对已标记物品使用core.catalog_testdata准备两名合成账户与import关系；已有关系/生产目标拒绝，服务器命令记录审计，不新增公开认领或默认用户。操作与边界见[验收说明](../ADMIN_DESKTOP.md#81-首次认领未开放时怎样准备售后验收)。


## 9. 验收数据重建与图片收口（已批准）

cece确认本期执行：清理无价值旧样例和全部历史图片，建立可重复灌入、可筛选剔除和整批清理的测试数据。起始代码为同分支正式后台交付；不修改生产数据，不将合成数据作为真实认领/配置/触碰证据。

- 新增007：test_batch保存批次及预期结果，test_batch_object保存对象来源；与可开关的生产验证标记分开，继承款式→发行→身份及后续办理/触碰。来源不因关闭验证开关丢失。真实测试卡不纳入自动样本或清理；跨批次及业务对象关联拒绝混用。
- 列表/工作台采用业务、测试、全部及批次筛选；默认业务。各项指标、趋势、明细和账户持有均应用相同数据范围。系统管理增加测试数据页签，不增顶级菜单；整批预览→确认删除，沿用写回执，失败/未知不冒充成功。
- 预置三类款式、固定/限时/非限定发行及约20身份，包含草稿/首配/售出未认领/持有/挂失/待办/多代换新转售和跨日期触碰。合成配置/触碰只由明确测试目标的命令准备，显式标注，不改变正常密钥算法、验签或认领服务。
- 废弃历史外链、旧域名映射、旧单件图片上传/读取/编辑。清理前完整备份数据库和私有图片；清理引用/元数据/已核验图片文件，不清理目录外文件、秘密或其他槽。新版款式图片及当前H5短许可/持续查看和安全边界保留。
- 执行先只读盘点，自动保留配置/密钥/计数/持有人等有价值事实，输出明确清单；旧样例按清单清理，不凭时间或名称猜测。未知对象保留。旧图片可全部清理，真实测试卡保留原配置及必要关系，图片重新维护。
- 备份/升级007、数据清理和代码部署分开；恢复不能覆盖后来数据。先隔离MySQL/浏览器验证灌入→操作→剔除→清理→重建，再在有有效通道、准确test目标和配套备份的前提下执行现有测试库。未部署、无连接或凭据过期时明确保留现场状态。
