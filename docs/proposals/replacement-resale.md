# D：挂失、换新与转售接续

审批范围：需求方向及正文明确标注的原则已确认，其余具体规则待cece审核。文档整理获批不等于本业务方案全部获批；本稿承载尚未纳入现行规范的改动，不能据此推定实现、验收、合并或部署。当前进展只看[TODO](../../TODO.md)，现行规则从[产品入口](../../PRD.md)查阅。

## 1 D：挂失、换新与转售的独立业务方案

**已确认目标：** 原数字身份及约定可接续权益保留 → 旧芯片挂失/停止服务 → 新实体及新芯片准备、配置、核验 → 正式接续 → 保留历史。转售必须换新实体；挂失换新通常是同持有人，转售则另有所有权变化，不能用换绑替代所有权转移。

| 概念 | 产品含义与当前限制 |
|---|---|
| 数字身份 | 可跨实体/芯片延续的数字对象；不能直接假定现有item已完整实现 |
| 实体载体 | 某一件实际服装/饰品，可能损坏/丢失/被替换；需辨识每次载体更换 |
| 芯片 | 某载体的认证入口；验签不证明合法持有人；同一数字身份同一时刻最多一个有效芯片，允许挂失后暂时没有有效芯片 |
| 当前持有人 | 经约定方式确认的权利主体，不能从碰卡或管理员录入直接推定；完整认领/所有权能力尚未交付 |
| 历次关联 | 哪枚芯片、哪件实体在何时承载过哪个数字身份，保留追溯但不授予历史卡当前访问权 |

现有schema在chip.item_id上唯一，停用/丢失也保留占用；首次绑定拒绝已被另一卡占用的物品。它支持现有唯一绑定，不足以直接表达“历次关联＋唯一当前授权”。技术方案需决定item与数字身份/实体载体的职责，不能仅去掉唯一约束或清空旧关联，不能把预留ownership/history表当已验收所有权服务。

| 必要业务动作 | 必须达到的结果／待设计部分 |
|---|---|
| 临时停用/恢复 | 阻断当前服务但保留关联，不代表丢失或替换；恢复检查对象、关联及当前授权。是否永久撤销停用前资格作为独立规则确认，不能因恢复自动假定安全 |
| 挂失/解除挂失 | 先按资格证据确认申请者，再阻断旧卡和已有资格；解除仅在尚未替换、无退役/争议等条件下考虑，资格与审批待定 |
| 永久退役 | 旧芯片不再获得该数字身份授权；不能通过普通“恢复”或重新登记生效 |
| 新芯片准备与核验 | 登记、配置、实卡验证是准备步骤，不等于对真实用户启用；需有不授予当前业务权益的核验路径，具体技术另审 |
| 正式接续 | 唯一当前授权切换与必要记录一致生效；旧卡永久退出，资格撤销不随状态恢复复活；不得留下双有效载体 |
| 接续失败/取消 | 明确发生在准备前、准备中或正式切换后；默认保持旧卡已挂失及新卡未激活的安全状态，恢复需明确条件，不自动让丢失旧卡复活 |

现有短凭证与持续查看资格都需覆盖；“每次查当前状态”不等于永久撤销。接续前已签发资格即使未使用也必须按规则失效；新卡正式接续后重新签发资格。方案需验证并发、响应丢失及恢复后的旧凭证，不只测新碰卡能打开网页。

同持有人换新不自动改变所有权，但须核对申请资格。转售必须按新实体履约及所有权确认规则处理，旧卡退役和持有人变更的完成时点要一致可解释；申请、支付/订单（如需要）、发货、签收与正式切换不预设同一时刻。哪些公开档案/权益延续、消耗型权益是否补回、私人资料是否隔离必须列清单，不复制旧芯片全部数据。当前无自动继承全部权益的承诺。

D待决定：申请和持有人资格证明；丢失/损坏换新的费用与次数；可接续权益清单和隐私边界；解除挂失条件；新实体确认及正式接续时点；履约失败/取消/争议处置。**转售必须换新实体已确定，不再列待选项。** 状态名称数量由业务动作推导，不自动增加一串枚举或完整交易平台。
