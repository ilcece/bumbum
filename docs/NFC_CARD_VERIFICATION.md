# 真实卡核验：先收集信息，再确认测试操作

目的：确认手里的芯片与工具能否实现既定动态防伪方案，避免仅看到链接或扫描登记成功，就当成防伪通过。本页是信息准备与后续验证边界，不是写卡、换钥匙、解锁或恢复出厂的操作说明。当前进度只在[TODO](../TODO.md)维护。

已知依据：既有验收记录使用NFC.cool 7.30、iOS 27.0.1；先写固定文本cece再批量读卡，6枚卡可登记且重扫不重复。另有开启随机UID/SUN的卡出现4字节随机标识。这里记录历史版本和现象，当前设备、标签型号和权限仍需重新核对，不证明SUN验签已通过。原证据见[技术说明第2.5节](../TECH_SPEC.md#25-手机扫描后自动登记)。

## 1. cece先回复这一批信息

先提供已经知道的事实；不确定就写“不知道”。可只查看现有信息页面，不为获取答案点击写入、改密钥、改权限、锁定、格式化或恢复。无需为了回报而读取或复制秘密。

| 信息 | 请提供什么 | 为什么需要 |
|---|---|---|
| 芯片身份 | 购买说明或型号文字；是否明确NTAG424 DNA、TagTamper或其他型号；厂家/供应商公开规格链接若有 | 不同型号和供应商预配置可能影响命令与权限；商品写着“NFC卡”不够判断 |
| 设备及工具 | 手机型号、当前iOS版本、NFC.cool版本；当前订阅级别或相关功能是否可用。已有电脑读写器/其他App则补型号版本，没有就写没有 | 核对当前操作能力，不把旧设备测试结果当作新版能力，也不要求先采购设备 |
| 测试卡数量与用途 | 可单独用于试验的卡有几枚，是否允许后续另行确认后改写；能否预留A/B/C三枚并用贴纸区分 | 先可用一枚探索；完整对照按现有规范需要同项目两枚、另一项目一枚，不等于现在增加饰品用户体验 |
| 各卡当前状态 | 按A/B/C写：空白、固定文本、普通链接或SUN；随机UID开/关/未知；是否改过密钥、是否锁定/只读、是否有原配置记录。密钥只回复“未改/已改且自己有安全备份/已改但未知/不知道”，不提供值 | 防止把未知旧卡当可任意重写的空卡，或覆盖已登记实物的配置。未知不等于可使用出厂默认密钥 |
| 工具可见能力 | 现有页面是否能看到标签信息/版本、真实UID（只报能否看到7字节，不必贴UID）、文件设置、SDM/SUN设置、Key Settings/ChangeKey等入口；可只提供不含秘密的菜单名称 | 区分“能读NDEF文本”“能启用SUN”“能分别配置密钥与权限”。看到入口不等于具备权限或已执行成功 |

回复模板（可直接复制，未知留未知）：

```text
芯片型号／购买说明：
手机型号／iOS：
NFC.cool版本／订阅或功能情况：
其他已有读写工具（无则写无）：
可预留测试卡数量：
A卡：内容类型／随机UID状态／是否改密钥及自己有无备份／锁定情况
B卡：同上
C卡：同上
现有可见的标签信息、SDM和密钥设置入口：
```

不要发送密钥、项目根密钥、全局K1、存储密钥、密码、二维码秘密、认证凭证或可直接访问的完整动态SUN链接。若页面把设置与秘密混在一起，只转述非秘密字段名及选项；不必发整页截图。UID不作为口令，但也不需要为第一轮信息收集公开完整业务卡编号。

## 2. 收到回复后，AI负责核对什么

下面是技术核验清单，供AI查资料和制定单卡测试方案；cece不需要先自行理解或计算这些参数。现阶段保持“待核验”，不预填推测值。

| 核验方向 | 需要固定的内容 | 证据与cece配合 |
|---|---|---|
| 型号和命令支持 | 实际芯片版本、标签类型、支持的NXP命令；供应商是否预配置/锁定 | AI核对型号对应官方资料；cece反馈公开型号或工具已有只读信息 |
| 密钥与权限 | K0管理、全局同版本K1、独立K2的既定职责是否能由实际权限实现；读取、写文件、改设置及换钥匙分别需要什么权限 | AI查具体版本文档；cece只确认有无所需权限和安全保存的原凭证，不在聊天提供密钥 |
| SDM文件设置 | 文件编号、通讯模式、读取/写入/修改权限；SDMMetaRead/SDMFileRead实际映射、UID与计数器镜像及随机UID选项 | 先用公开资料和去秘密的现有设置核对，不靠字段名称猜权限，不先改卡 |
| 动态链接和字节位置 | `/tap?picc_data=...&cmac=...`的完整NDEF编码、参数长度、大小写、各镜像位置、MAC输入起点/输出位置、文件容量及计数器限制 | AI根据目标工具实际编码计算并逐字节核验，不能用界面中文字数估算位置；只用占位或合成样例讨论 |
| 加密计算 | K0/K2/K3/K4派生算法及输入编码；PICC解密、会话密钥、CMAC输入与截断、UID/计数器字节序 | AI选成熟库、核对官方资料及已知答案测试；不自行设计协议或把任意解密结果当真实UID |
| 工具实际能力 | 能否逐项设置上述权限/位置、分别写入密钥、读取配置、验证结果和保留安全操作记录 | 先确认工具能力；缺功能时说明具体缺项和替代工具成本，再对齐，不先采购或切换方案 |
| 失败与恢复前提 | 哪些步骤可能使卡不可再修改，失败时凭什么恢复；原配置/凭证是否安全保存，卡片能否仅用于试验 | AI给出每步成功、失败与停止条件；未知原密钥或锁定状态先停止改写，不承诺恢复出厂能解决 |
| 配置完成证据 | 既有provisioned_at如何与配置版本、核对结果及操作记录对应；怎样区分已生成密钥、写卡完成和验证通过 | 先定义最小记录办法，再判断现有表是否够用；如需改表，单独对齐迁移，不提前新增字段 |
| 测试访问环境 | 手机可访问的HTTPS测试地址、用户路径与管理入口隔离、运行配置与测试库归属 | AI设计本地/测试环境验证；实际服务器检查和部署另行授权，不假设可直连ECS |

已确认的方案不重新开放选择：同版本跨项目共享K1、每枚芯片独立K2；登记接口不临时解密随机UID/SUN卡。具体冲突若被官方资料或实卡证据证实，再说明影响与备选方案。资料来源、版本、日期和结果记入现有技术附录/CHANGELOG，不新建另一套状态记录。

## 3. 后续实测怎样分步通过

收到第1节信息后，AI先给固定参数、工具步骤、影响范围、必要备份和停止/恢复条件，cece确认后才开始真实卡操作。本页不构成对改写、换钥匙或服务器部署的授权。

1. **一枚卡探索**：只用明确可改写的专用测试卡；按批准步骤配置，核对读出的加密数据、真实身份及计数器，形成正确答案对照。能打开网址或读到14位十六进制不算通过。
2. **三枚卡对照**：同项目A/B、另一项目C；验证同版本K1一致、不同卡K2独立，项目与物品匹配。只记录“相同/不同”和安全存放位置，不公开密钥。
3. **正常与失败核验**：真实读数通过；改动防伪码、错误密钥、旧链接、停用和缺少配置不能取得新的有效授权。系统故障显示故障，不显示为假货。
4. **可重复和记录**：再次触碰、刷新旧链接、重启服务后结果符合规则；数据库记录、配置完成证据和人工操作对应。不可用配置不标成写卡完成。

若工具能力、权限或测试卡数量不足，明确哪些已验证、哪些受阻；可以继续绑定和页面联调，不把合成测试计为真实卡验收。
